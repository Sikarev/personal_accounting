# Соглашения API

Контракт — [`api/openapi.yaml`](../api/openapi.yaml) (OpenAPI 3.0.3). Он первичен: сначала меняется контракт, потом по нему генерируется код сервера (`oapi-codegen`) и клиента (`orval`).

## Адреса и версии

- Все доменные маршруты — под `/api/v1` (`servers[0].url` в контракте). В `paths` пути указаны **без** префикса: `/currencies` обслуживается по адресу `/api/v1/currencies`. Клиенту базовый адрес нужно задать отдельно (в orval — `baseUrl`).
- Версия в пути меняется только при несовместимых изменениях. Совместимые изменения (новый эндпоинт, новое необязательное поле в ответе, новый код ошибки) делаются в той же версии — клиент обязан игнорировать неизвестные поля.
- `/healthz` — служебный адрес для проверок доступности (Docker, балансировщик). Он вне `/api` и **не входит в контракт**: это не часть API для клиентов, а у контракта общий префикс `/api/v1`.
- Пути — во множественном числе, в kebab-case: `/accounts`, `/exchange-rates`, `/accounts/{accountId}`.

## Формат данных

| Что | Как | Пример |
|---|---|---|
| Имена полей JSON | camelCase | `minorUnits`, `toAccountId` |
| Идентификаторы | строка uuid | `"0193b7c2-1f7e-7c4e-9a51-3c2d1e0f9a8b"` |
| Деньги | целое число в минимальных единицах + код валюты рядом | `{"amount": 35050, "currency": "RUB"}` = 350,50 ₽ |
| Дата операции | строка `YYYY-MM-DD` (без времени и пояса) | `"2026-11-18"` |
| Момент времени | строка RFC 3339 с поясом | `"2026-11-18T09:15:00Z"` |
| Перечисления | строки в snake_case | `"credit_card"` |

- Деньги никогда не передаются дробным числом. Сколько знаков после запятой у валюты — поле `minorUnits` справочника `GET /api/v1/currencies`.
- Суммы в API **положительные**; направление задаёт тип операции. Знак в БД расставляет сервер (см. [data-model.md](data-model.md)).
- Отсутствующее значение — поле не передаётся или `null`; в схеме это `required` / `nullable`.

## Списки и пагинация

Ответ со списком — всегда объект, а не массив: `{"items": [...]}`. Так в ответ можно добавить поля, не ломая клиентов.

Длинные списки (лента операций и т. п.) — курсорная пагинация:

- запрос: `?limit=50&cursor=<строка>`; `limit` — необязательный, у каждого эндпоинта свой максимум;
- ответ: `{"items": [...], "nextCursor": "<строка>"}`; `nextCursor` отсутствует, если это последняя страница;
- курсор непрозрачен для клиента: его не разбирают и не собирают, а передают как есть.

Курсор, а не `offset`, — потому что при добавлении операций смещение «съезжает» и записи на границе страниц дублируются или пропадают.

Короткие справочники (валюты) отдаются целиком, без пагинации, но в том же формате `{"items": [...]}`.

## Ошибки

Все ошибки под `/api` — в формате [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) (Problem Details), `Content-Type: application/problem+json`. Это касается и неизвестных адресов, и неподдерживаемых методов, и ошибок разбора и проверки запроса.

```json
{
  "type": "about:blank",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "Некорректные данные запроса.",
  "code": "validation_failed",
  "errors": [
    {"field": "amount", "code": "required", "message": "Обязательное поле."}
  ]
}
```

| Поле | Смысл |
|---|---|
| `type` | пока всегда `about:blank` |
| `title` | стандартная фраза HTTP-статуса |
| `status` | HTTP-статус |
| `detail` | пояснение для разработчика и запасной текст |
| `code` | **машиночитаемый код** — по нему клиент выбирает текст для пользователя |
| `errors` | только при `validation_failed`: ошибки по полям |

`errors[].field` — путь к полю в camelCase через точку (`amount`, `splits.0.amount`) или имя параметра запроса (`limit`). Формат совпадает с путями полей в `@mantine/form`, ошибку можно сразу показать у поля. `errors[].code` — вид нарушения: `required`, `invalid_type`, `invalid_value` (не из enum), `invalid_format`, `too_long`, `too_short`, `too_large`, `too_small`, `too_many_items`, `too_few_items`, `unknown_field`, `invalid` (прочее); сервисный слой добавляет свои.

Коды ошибок (список расширяется; неизвестный код клиент обрабатывает по HTTP-статусу):

| `code` | Статус | Когда |
|---|---|---|
| `bad_request` | 400 | запрос не удалось разобрать: невалидный JSON, тело там, где его быть не должно |
| `validation_failed` | 422 | запрос разобран, но данные не прошли проверку; подробности в `errors` |
| `unauthorized` | 401 | нет действующей сессии: cookie нет, сессия истекла, удалена или пользователь вышел |
| `invalid_credentials` | 401 | вход: неверный e-mail или пароль (один ответ на оба случая) |
| `forbidden_origin` | 403 | запрос, меняющий данные, пришёл со страницы другого сайта (защита от CSRF) |
| `not_found` | 404 | адрес или объект не найден (в т. ч. объект чужой семьи — не 403, чтобы не раскрывать факт существования) |
| `method_not_allowed` | 405 | метод не поддерживается для адреса; список допустимых — в заголовке `Allow` |
| `too_many_requests` | 429 | превышен лимит частоты; через сколько секунд повторить — в заголовке `Retry-After` |
| `account_has_transactions` | 409 | удаление счёта, на который ссылается хоть одна операция (в т. ч. удалённая или как получатель перевода); такой счёт можно только архивировать |
| `account_archived` | 409 | корректировка остатка архивного счёта; сначала его нужно вернуть из архива |
| `internal` | 500 | непредвиденная ошибка |

**409 или 422.** 422 — исправь поля запроса (подсветка у полей). 409 `Conflict` — запрос корректен, но действие невозможно в текущем состоянии объекта; полей, которые можно исправить, нет. У каждого 409 свой `code`, по нему клиент показывает текст; в Go — `problem.Conflict(code, detail)`, коды — константы в `internal/problem`.

Коды бизнес-правил в `errors[].code` (ошибки полей при `validation_failed`):

| `errors[].code` | Поле | Когда |
|---|---|---|
| `email_taken` | `email` | регистрация на уже занятый e-mail |
| `invalid_token` | `token` | токен из письма неверный, просрочен, уже использован, выдан для другого назначения или для прежнего адреса пользователя (причина не уточняется) |

**Почему 422, а не 400.** 400 — «запрос не понят»: это ошибка в клиентском коде, пользователю показать нечего. 422 — «понят, но данные не подходят»: клиент подсвечивает поля из `errors`. Разные статусы позволяют клиенту обрабатывать два случая по-разному, не разбирая тело. 422 возвращается для любых `validation_failed` — и от проверки по контракту, и от бизнес-правил.

При 500 клиент получает только общий текст. Подробности (текст ошибки, SQL, стек) пишутся в лог вместе с request id. Request id сервер возвращает в заголовке `X-Request-Id` — по нему ошибку пользователя находят в логах. Клиент может прислать свой `X-Request-Id` (до 64 символов `A-Za-z0-9._-`), иначе сервер сгенерирует его сам.

Если клиент сам отменил запрос (закрыл соединение), это не ошибка сервера: в лог пишется уровень info и статус 499.

В Go ошибка с известным кодом — это `*problem.Problem` из `internal/problem`: обработчик возвращает её как обычную ошибку (`return nil, problem.NotFound("Счёт не найден.")`). Любая другая ошибка превращается в 500. У `problem.TooManyRequests(d)` длительность уходит в заголовок `Retry-After` (секунды, с округлением вверх).

## Авторизация

Вход — по e-mail и паролю (`POST /auth/register`, `/auth/login`, `/auth/logout`, `GET /me`). Сессии хранятся в Postgres (таблица `sessions`), браузер держит только случайный токен в cookie. Подтверждение e-mail и сброс пароля — по ссылке из письма, см. «Подтверждение e-mail и сброс пароля».

### Cookie сессии

- Имя `pa_session`, значение — 32 случайных байта (`crypto/rand`) в base64url. В БД — только SHA-256 токена: утечка базы не даёт войти по чужой сессии.
- Флаги: `HttpOnly` (JavaScript её не видит), `SameSite=Lax`, `Path=/api` (не уходит с запросами за статикой), `Secure` — по настройке `COOKIE_SECURE` (по умолчанию включён в production и выключен в development, где API работает по http).
- Срок — 30 дней, **скользящий**: если с прошлого продления прошло больше часа, любой запрос с сессией продлевает `expires_at` и присылает обновлённый `Set-Cookie`. Просроченная сессия равна отсутствующей: при обращении она удаляется, ответ — 401.
- Регистрация и вход выдают новую сессию (вход при этом удаляет прежнюю сессию этого браузера), выход удаляет сессию из БД и стирает cookie (`Max-Age=0`). Выход идемпотентен: без сессии тоже 204.
- В сессии сохраняются `ip` (реальный, см. ниже) и `user_agent` (до 512 байт).

Пароли — argon2id (OWASP: m=19456 KiB, t=2, p=1, соль 16 байт, ключ 32 байта) в PHC-строке `$argon2id$v=19$m=…,t=…,p=…$соль$хеш`: параметры записаны в самом хеше, их можно поменять, не ломая старые. Длина пароля — 8–128 символов. При входе с несуществующим e-mail сервер всё равно проверяет пароль против фиктивного хеша, чтобы время ответа не выдавало, есть ли аккаунт.

### Какие операции требуют входа

Решает **контракт**, а не список путей в коде. В `openapi.yaml` глобально задано `security: [cookieAuth: []]` — по умолчанию каждая операция требует сессии. Публичная операция явно переопределяет это:

```yaml
  /currencies:
    get:
      operationId: listCurrencies
      security: []        # без входа
```

Сейчас публичные: `listCurrencies`, `register`, `login`, `logout`, `verifyEmail`, `requestPasswordReset`, `confirmPasswordReset`. Тест `TestContractSecurity` фиксирует этот список — новая публичная операция добавляется в него осознанно.

Middleware `authenticate` (`internal/httpapi/session.go`) находит операцию контракта для запроса и, если она не публичная, проверяет cookie. Нет действующей сессии — 401 `unauthorized` (и стирание мёртвой cookie) до валидатора и обработчика.

### Текущий пользователь в обработчике

```go
func (s *server) ListAccounts(ctx context.Context, req oapi.ListAccountsRequestObject) (oapi.ListAccountsResponseObject, error) {
	p := currentUser(ctx) // Principal{UserID, FamilyID, Role}
	rows, err := s.q.ListAccounts(ctx, dbgen.ListAccountsParams{FamilyID: p.FamilyID, UserID: p.UserID})
	...
}
```

`family_id` для запросов к доменным таблицам берётся **только** из `currentUser(ctx)`, никогда из тела или параметров запроса. `currentUser` паникует (→ 500), если вызвать его в публичной операции: это ошибка в коде, а не запрос клиента.

### Защита от CSRF

На всё под `/api` стоит `http.CrossOriginProtection` из стандартной библиотеки Go. Запросы, меняющие данные (POST, PUT, PATCH, DELETE), пропускаются, если:

- браузер прислал `Sec-Fetch-Site: same-origin` или `none`;
- или (браузеры без `Sec-Fetch-Site`, страница по http не на localhost) `Origin` совпадает с `Host`;
- или заголовков нет вовсе — запрос не из браузера (curl, серверный клиент); от CSRF защищать нечего.

Иначе — 403 `forbidden_origin`. `GET`/`HEAD` не проверяются: они не меняют данных. Вместе с `SameSite=Lax` это закрывает CSRF без токенов в формах.

Dev-сценарий проходит без настроек: страница на `localhost:5173`, Vite проксирует `/api` на `:8080`, браузер видит один origin и шлёт `same-origin`. С телефона (`http://192.168.x.x:5173`) `Sec-Fetch-Site` не приходит, но прокси Vite сохраняет `Host`, и он совпадает с `Origin`. Если фронт когда-нибудь окажется на другом origin, его можно разрешить переменной `CSRF_TRUSTED_ORIGINS` (через запятую, например `http://localhost:5173`).

### Ограничение частоты

| Что | Лимит | Ключ |
|---|---|---|
| `register` и `login` | 20 запросов в минуту | IP (для IPv6 — сеть /64) |
| `login` | 5 попыток за 15 минут; успешный вход сбрасывает счёт | e-mail + IP |
| `login` | 50 **неудачных** попыток в час; успешный вход счёт не сбрасывает | e-mail (со всех адресов) |
| `requestPasswordReset` | 20 запросов в час | IP |
| `requestPasswordReset` | 3 письма в час; превышение ответ **не** меняет (202), письмо просто не уходит | e-mail |
| `verifyEmail` и `confirmPasswordReset` | 20 запросов в минуту (общий) | IP |
| `resendVerificationEmail` | 1 в минуту и 5 в час | пользователь |

E-mail в ключах — в нижнем регистре. Окно скользящее. Превышение любого лимита (кроме лимита писем сброса на адрес) — 429 `too_many_requests` с `Retry-After`. Лимит сброса на адрес не даёт 429, иначе ответ выдавал бы, что адрес недавно запрашивали, — то есть что аккаунт, скорее всего, есть. Он учитывается для любых адресов, зарегистрированных и нет.

Лимиты задаются в `httpapi.Limits`, умолчания — `defaultLimits` в `internal/httpapi/router.go`.

- Лимит по IP стоит до проверки по контракту: невалидные запросы тоже его расходуют. Запрос входа с невалидным e-mail (в т. ч. с управляющими символами) отклоняется проверкой по контракту (422) и лимиты по e-mail не расходует.
- Лимит «e-mail + IP» учитывает попытку до проверки пароля, поэтому параллельные запросы не проскакивают его, пока считается хеш. IP в ключе нужен, чтобы посторонний не мог неверными паролями со своего адреса заблокировать владельцу вход с его адреса.
- Общий лимит на e-mail защищает от распределённого перебора с многих адресов.
- Несуществующий e-mail считается так же, как существующий.

**Остаточный риск:** распределённая атака (50 неудачных попыток в час с разных адресов) по-прежнему может заблокировать вход в чужой аккаунт — со всех адресов, включая адрес владельца, пока атака продолжается. Это цена защиты от распределённого перебора; смягчить можно позже (например, вход по ссылке из письма в обход лимита).

**Ограничение MVP:** счётчики живут в памяти процесса (`internal/ratelimit`). При нескольких экземплярах API у каждого свой счёт, после перезапуска счёт обнуляется. Для нескольких экземпляров понадобится общее хранилище (Postgres или Redis). Старые ключи удаляются раз в окно, память не растёт без предела. Лимиты и часы подменяются в тестах через `httpapi.Options`.

### Подтверждение e-mail и сброс пароля

| Операция | Вход | Ответ |
|---|---|---|
| `POST /auth/verify-email` `{token}` | не нужен (ссылку могут открыть в другом браузере) | 204 |
| `POST /auth/verify-email/resend` | нужен | 204; если e-mail уже подтверждён — тоже 204, письмо не отправляется |
| `POST /auth/password-reset` `{email}` | не нужен | **всегда** 202 без тела — есть такой аккаунт или нет |
| `POST /auth/password-reset/confirm` `{token, password}` | не нужен | 200 `Me` + новая cookie сессии |

Подтверждение **мягкое**: без него приложением можно пользоваться (`GET /me` отдаёт `emailVerified`). Письмо подтверждения отправляется при регистрации (после коммита транзакции) и по `resend`.

**Токены** (таблица `email_tokens`):
- 32 случайных байта в base64url (как у сессий), в БД — только SHA-256;
- сроки: подтверждение — 24 часа, сброс — 1 час (`verifyEmailTokenTTL`, `resetPasswordTokenTTL` в `internal/httpapi/email.go`; те же сроки — в текстах писем);
- одноразовые: погашение — один `UPDATE … WHERE used_at IS NULL AND expires_at > now RETURNING`, поэтому из двух одновременных запросов с одним токеном успешен только один;
- новый токен того же назначения удаляет прежние: действует только ссылка из последнего письма. Выдача токена блокирует строку пользователя (`SELECT … FOR UPDATE`), чтобы одновременные запросы не оставили два действующих токена;
- токен привязан к адресу, на который ушло письмо: если `users.email` сменился, токен недействителен;
- любой неподходящий токен — 422 `validation_failed` с ошибкой `invalid_token` у поля `token`.

**Сброс пароля** в одной транзакции гасит токен, меняет хеш пароля (правила — как при регистрации: 8–128 символов), подтверждает e-mail (владение адресом доказано), удаляет **все** сессии пользователя и создаёт новую. После коммита сбрасываются счётчики неудачных входов для этого e-mail и счётчик «e-mail + IP» для текущего IP (с других IP — нет: их ключи не перечислить, они истекут сами). Токен проверяется до расчёта хеша пароля: argon2id не считается для заведомо неверных токенов.

**Время ответа `password-reset`** не должно выдавать, есть ли аккаунт. В обработчике в обоих случаях — только поиск пользователя; токен создаётся и письмо отправляется в фоне.

**Ссылки в письмах:** `APP_BASE_URL` + `/verify-email?token=…` и `/reset-password?token=…` — это маршруты фронтенда; страница берёт `token` из адреса и отправляет его в API.

### Письма

Пакет `internal/mail`:
- `Mailer` — интерфейс отправки. Реализации: `SMTP` (стандартная `net/smtp`, учитывает таймаут контекста; STARTTLS, если сервер предлагает; вход PLAIN, если задан `SMTP_USERNAME`), `Memory` (запоминает письма, для тестов), `Discard`;
- письмо — `multipart/alternative`: `text/plain` и простой HTML (`html/template` экранирует подставленные значения), UTF-8, тело в quoted-printable, заголовки с кириллицей — encoded-word (`mime.QEncoding`);
- `Background` отправляет письма в фоне: каждое — в своей горутине с таймаутом 30 с (`mailSendTimeout` в `cmd/api`), ошибка — в лог (`mail: send failed` / `mail: prepare failed`) с `kind`, `user_id`, `request_id`; ни токен, ни ссылка, ни адрес в лог не попадают. При остановке сервер сначала дожидается текущих запросов, потом закрывает отправку (`Background.Close`: новые письма больше не запускаются, в лог — `mail: dropped, sender closed`) и ждёт писем, отправка которых уже началась (до 10 с). Тесты дожидаются писем через `Background.Wait`, без `time.Sleep`;
- адрес получателя разбирается `net/mail.ParseAddress`, в `RCPT TO` и `To` уходит только сам адрес. Валидатор контракта (`format: email`) принимает только адреса, которые `ParseAddress` разбирает в ту же строку, — иначе регистрация прошла бы, а письма молча не уходили бы.

В разработке письма принимает Mailpit (см. README). Production-провайдер выбирается на этапе 6.

**Ограничения MVP:** очереди писем (outbox) нет — письмо, отправка которого не закончилась до падения процесса, теряется; пользователь запросит его ещё раз. Ошибка SMTP клиенту не видна (ответ уже отправлен), только в логе.

### Реальный IP клиента

Middleware `withClientInfo` (первое в цепочке) определяет IP и кладёт его в контекст. IP используется в лимитах, в `sessions.ip` и в логе запросов (поле `ip`).

- Настройка `TRUSTED_PROXIES` — CIDR или отдельные IP через запятую (`10.0.0.0/8,172.16.0.1`), по умолчанию пусто.
- Если адрес соединения **не** из списка, клиент — сам адрес соединения, `X-Forwarded-For` игнорируется: его может прислать кто угодно.
- Если из списка — `X-Forwarded-For` читается справа налево (каждый прокси дописывает адрес в конец), доверенные адреса пропускаются, первый недоверенный — клиент. Значения левее него мог подделать сам клиент.

`middleware.RealIP` из chi не используется: он безусловно доверяет `X-Forwarded-For`.

## Проверка запросов

Запрос проверяется в два слоя.

**1. Контракт** — middleware `requestValidator` (kin-openapi) по спецификации, встроенной в бинарник (`oapi.GetSpec`). Срабатывает до обработчика, ответ — 422 `validation_failed` с `errors[]` по всем полям сразу (или 400, если тело не JSON). Проверяет всё, что выражается схемой:

- обязательные поля и параметры (`required`);
- типы, `enum`, `format` (`uuid`, `date`, `date-time`), `pattern`;
- `minLength`/`maxLength`, `minimum`/`maximum`, `minItems`/`maxItems`;
- лишние поля — **соглашение:** у каждого объекта в теле запроса `additionalProperties: false`, иначе опечатка в имени поля молча проигнорируется. Тест `TestContractRequestBodiesForbidAdditionalProperties` проверяет это для всего контракта;
- тело у операции без `requestBody` — 400.

Ответы по контракту не проверяются.

**2. Сервисный слой** — всё, что зависит от данных и пользователя:

- принадлежность семье: каждый запрос фильтрует по `family_id` из сессии; чужой объект — 404;
- видимость личных счетов;
- бизнес-правила: тип категории соответствует типу операции, глубина дерева категорий ≤ 2, у перевода разные счета, удаление счёта только без операций и т. п.

Ошибки сервисного слоя — тоже `problem.Validation(...)` с полями (или `problem.NotFound`, `problem.Conflict`), формат для клиента один.

`uniqueItems` (повторы в массиве) валидатор сообщает кодом `invalid` — отдельного кода для него нет.

## Счета

Операции — в контракте (тег `accounts`), код — `internal/httpapi/accounts.go`, SQL — `internal/db/queries/accounts.sql`.

- **Видимость.** Пользователь видит общие счета семьи и свои личные (`owner_user_id IS NULL OR owner_user_id = :user`). Чужой личный счёт и счёт чужой семьи — 404 на **любой** операции, включая `PUT /accounts/order` и `adjust-balance`. Общие счета меняет любой участник семьи. В ответе `visibility: private` значит «личный счёт текущего пользователя» — чужие личные в ответы не попадают.
- **Список** (`GET /accounts`) — все видимые счета, включая архивные; фильтрует клиент. Порядок: `sortOrder`, `created_at`, `id`. Остаток и `hasTransactions` считаются в том же запросе (без N+1).
- **Порядок.** Новый счёт получает `sortOrder` = максимум в его группе + 1 (общие и личные пользователя — разные группы). `PUT /accounts/order` ставит `sortOrder` = позиция в списке (с 0) в одной транзакции; хоть один невидимый или несуществующий id — 404, ничего не меняется. Номера в разных группах могут совпадать: группы показываются раздельно.
- **Корректировка** (`adjust-balance`): счёт блокируется (`SELECT … FOR UPDATE`), затем считается остаток, создаётся операция `adjustment` на разницу и запись в `audit_log` — в одной транзакции. Блокировка не даёт двум одновременным корректировкам посчитать разницу от одного остатка. Дата — «сегодня» в поясе пользователя (`users.timezone`). Разница 0 — операции нет, в ответе нет `transactionId`.
- **Удаление** — тоже под блокировкой счёта: проверка «нет операций» и `DELETE` в одной транзакции; нарушение внешнего ключа (операция появилась в обход блокировки) тоже даёт 409.
- **Имя** обрезается от пробелов; длину 1–100 проверяет контракт до обрезки, пустое после обрезки — `required`.
- **Суммы** в запросах (`initialBalance`, `balance`) — схема `MoneyAmount`: `int64` в пределах ±10^15, чтобы сумма остатков не переполнялась.

## Как добавить эндпоинт

Все команды — из каталога `api/`.

1. **Контракт.** Опиши операцию в `openapi.yaml`: `operationId` в camelCase (из него получится имя метода); операция по умолчанию требует входа, публичную помечай `security: []`; схемы запроса и ответа в `components/schemas`, ответ `default: $ref: "#/components/responses/Problem"`. Всё, что можно выразить схемой, выражай в ней (`required`, `enum`, `maxLength`, `minimum`, `format`), у объектов тела — `additionalProperties: false`: эти проверки выполнит валидатор, в обработчике их не повторяй.
2. **Генерация сервера.** `go generate ./...` — обновит `internal/oapi/oapi.gen.go` и встроенную спецификацию. Сборка упадёт на строке `var _ oapi.StrictServerInterface = (*server)(nil)` в `internal/httpapi/server.go`, пока метод не реализован, — так и задумано.
3. **SQL.** Добавь запрос в `internal/db/queries/<область>.sql` с аннотацией `-- name: GetAccount :one` (`:one`, `:many`, `:exec`). Каждый запрос к доменным таблицам фильтрует по `family_id`. Снова `go generate ./...` — sqlc обновит `internal/db/dbgen`. Если удалил `.sql`-файл, удали и его `.sql.go` в `dbgen`: sqlc старые файлы не стирает.
4. **Обработчик.** Реализуй метод `server` в `internal/httpapi/<область>.go`: возьми текущего пользователя (`currentUser(ctx)`, см. «Авторизация»), проверь бизнес-правила, вызови запрос из `s.q` (несколько изменений — в транзакции, см. ниже), преобразуй строки БД в типы `oapi`, верни типизированный ответ (`oapi.GetAccount200JSONResponse{...}`) или ошибку (`*problem.Problem` либо любую другую → 500). Для пустых списков создавай срез через `make`, чтобы в JSON был `[]`, а не `null`.
5. **Тест.** В `internal/httpapi/*_test.go`: роутер через `newRouter(t, logger, testdb.Pool(t))` (или `newAuthEnv(t, Options{...})` — с подменёнными часами и помощниками `register`/`send`, см. `auth_test.go`), запрос через `httptest`. Защищённой операции нужна cookie: `cookie, _ := e.register(t, uniqueEmail())`, затем `e.send(..., withCookie(cookie))`. Проверяй сырой JSON (имена полей), коды ошибок, бизнес-правила, изоляцию семей и видимость личных счетов. Правила схемы отдельно тестировать не нужно — их покрывают тесты валидатора.
6. **Проверка.** `gofmt -l .` (пусто), `go vet ./...`, `go test ./...`. Сгенерированный код коммитится вместе с изменением: CI проверяет, что `go generate ./...` не даёт diff.

### Транзакции

`server` хранит пул (`s.pool`) и запросы (`s.q`, `*dbgen.Queries`). Одиночный запрос — через `s.q`. Несколько изменений, которые должны примениться вместе (операция + запись в журнал изменений), — в транзакции:

```go
tx, err := s.pool.Begin(ctx)
if err != nil {
	return nil, err
}
// Rollback после Commit ничего не делает, поэтому defer безопасен:
// при любом раннем return транзакция откатится.
defer tx.Rollback(ctx)

q := s.q.WithTx(tx) // те же запросы, но внутри транзакции
if err := q.CreateTransaction(ctx, ...); err != nil {
	return nil, err
}
if err := q.InsertAuditLog(ctx, ...); err != nil {
	return nil, err
}
if err := tx.Commit(ctx); err != nil {
	return nil, err
}
```

## Соответствие типов

| PostgreSQL | Go (sqlc, `dbgen`) | OpenAPI | Go (oapi-codegen, `oapi`) |
|---|---|---|---|
| `uuid` | `uuid.UUID` | `string, format: uuid` | `openapi_types.UUID` (= `uuid.UUID`) |
| `bigint` (деньги) | `int64` | `integer, format: int64` | `int64` |
| `integer` / `smallint` | `int32` / `int16` | `integer` | `int` (с `format: int32` — `int32`) |
| `text`, `char(3)` | `string` | `string` | `string` |
| `boolean` | `bool` | `boolean` | `bool` |
| `date` | `time.Time` (полночь UTC) | `string, format: date` | `openapi_types.Date` — обёртка: `openapi_types.Date{Time: d}`, обратно `.Time` |
| `timestamptz` | `time.Time` | `string, format: date-time` | `time.Time` |
| `inet` | `netip.Addr` (NULL — `*netip.Addr`) | — | — |
| `numeric` (курсы) | `pgtype.Numeric` | `string` (десятичная запись, без потери точности) | `string`; формат уточняется на этапе 4 |
| enum (`account_type` и др.) | свой строковый тип (`dbgen.AccountType`) | `string, enum: [...]` | свой строковый тип в `oapi` — преобразование через `string(...)` |
| NULL-колонка | указатель (`*string`, `*time.Time`, `*uuid.UUID`) | необязательное поле или `nullable: true` | указатель |

`date` переопределён на `time.Time` (а не `pgtype.Date`), потому что `openapi_types.Date` — тоже обёртка над `time.Time`: преобразование — одна строка без проверки `Valid`. Переопределения — в `api/sqlc.yaml`.

## Инструменты генерации

`oapi-codegen` и `sqlc` закреплены в `api/go.mod` директивой `tool` и запускаются через `go tool <имя>` — отдельно ставить их не нужно, версия у всех одна.

| Инструмент | Конфиг | Результат |
|---|---|---|
| `oapi-codegen` (strict server для chi + встроенная спецификация) | `internal/oapi/oapi-codegen.yaml` | `internal/oapi/oapi.gen.go` |
| `sqlc` (pgx/v5) | `sqlc.yaml`; схема — прямо из `migrations/` | `internal/db/dbgen/` |

Клиент для фронтенда генерирует `orval` (devDependency в `web/package.json`): `pnpm generate:api` из `web/`.

| Инструмент | Конфиг | Результат |
|---|---|---|
| `orval` (хуки TanStack Query, `fetch`) | `web/orval.config.ts` | `web/src/shared/api/generated/` |

Базовый адрес `/api/v1` задан в конфиге orval (`baseUrl`), пути берутся из `paths`. Имя хука — из `operationId`: `listCurrencies` → `useListCurrencies()`. Запросы идут через свой мутатор `web/src/shared/api/http.ts`: он превращает Problem Details в `ApiError` с полями `status`, `code` (любая строка, не только перечисленные в контракте), `detail`, `fieldErrors` (`errors[]` → `{ поле: текст }`) и `requestId` (из `X-Request-Id`). Сгенерированный код коммитится, CI (`web.yml`) проверяет, что он совпадает с контрактом.

Сгенерированный код (Go и web) в `.gitattributes` помечен `eol=lf`: генераторы пишут LF, и с `core.autocrlf=true` на Windows иначе появлялся бы фиктивный дифф.

`sqlc` на Windows работает без gcc: при сборке без cgo он использует парсер Postgres, скомпилированный в WebAssembly (`wasilibs/go-pgquery`). CI запускает генерацию так же (`CGO_ENABLED=0`).

## Прочее

- `HEAD` на любой ресурс с `GET` работает (chi `middleware.GetHead`), ответ 405 содержит заголовок `Allow`.
- Реальный IP клиента — только от доверенных прокси (`TRUSTED_PROXIES`), см. «Авторизация → Реальный IP клиента».
- Поле `format: email` в контракте генерируется как `openapi_types.Email`, который проверяет формат сам и без обрезки пробелов. Поэтому у полей e-mail стоит `x-go-type: string`, а формат проверяет валидатор контракта (`validator.go`, пробелы по краям допускаются — сервер их обрезает).
- `oapi-codegen` во встроенной спецификации (`oapi.GetSpec`) пишет `operationId` с заглавной буквы (`Register`). Для сравнения с контрактом есть `operationID(route)`.
- Успешные `GET /healthz` не пишутся в лог запросов (их шлёт балансировщик каждые несколько секунд); неуспешные пишутся, причина отказа БД — отдельной строкой уровня warn.
