# Соглашения API

Контракт — [`api/openapi.yaml`](../api/openapi.yaml) (OpenAPI 3.0.3). Он первичен: сначала меняется контракт, потом по нему генерируется код сервера (`oapi-codegen`) и клиента (`orval`).

## Адреса и версии

- Все доменные маршруты — под `/api/v1` (`servers[0].url` в контракте). В `paths` пути указаны **без** префикса: `/currencies` обслуживается по адресу `/api/v1/currencies`. Клиенту базовый адрес нужно задать отдельно (в orval — `baseUrl`).
- Версия в пути меняется только при несовместимых изменениях. Совместимые изменения (новый эндпоинт, новое необязательное поле в ответе, новый код ошибки) делаются в той же версии — клиент обязан игнорировать неизвестные поля.
- `/healthz` — служебный адрес для проверок доступности (Docker, балансировщик). Он вне `/api` и **не входит в контракт**: это не часть API для клиентов, а у контракта общий префикс `/api/v1`.
- Пути — во множественном числе, в kebab-case: `/accounts`, `/exchange-rates`, `/accounts/{accountId}`.

## Формат данных

| Что | Как | Пример |
|---|---|---|
| Имена полей JSON | camelCase | `minorUnits`, `toAccountId` |
| Идентификаторы | строка uuid | `"0193b7c2-1f7e-7c4e-9a51-3c2d1e0f9a8b"` |
| Деньги | целое число в минимальных единицах + код валюты рядом | `{"amount": 35050, "currency": "RUB"}` = 350,50 ₽ |
| Дата операции | строка `YYYY-MM-DD` (без времени и пояса) | `"2026-11-18"` |
| Момент времени | строка RFC 3339 с поясом | `"2026-11-18T09:15:00Z"` |
| Перечисления | строки в snake_case | `"credit_card"` |

- Деньги никогда не передаются дробным числом. Сколько знаков после запятой у валюты — поле `minorUnits` справочника `GET /api/v1/currencies`.
- Суммы в API **положительные**; направление задаёт тип операции. Знак в БД расставляет сервер (см. [data-model.md](data-model.md)). Исключения — остатки счёта и `amount` корректировки остатка.
- Отсутствующее значение — поле не передаётся или `null`; в схеме это `required` / `nullable`.

## Списки и пагинация

Ответ со списком — всегда объект, а не массив: `{"items": [...]}`. Так в ответ можно добавить поля, не ломая клиентов.

Длинные списки (лента операций и т. п.) — курсорная пагинация:

- запрос: `?limit=50&cursor=<строка>`; `limit` — необязательный, у каждого эндпоинта свой максимум;
- ответ: `{"items": [...], "nextCursor": "<строка>"}`; `nextCursor` отсутствует, если это последняя страница;
- курсор непрозрачен для клиента: его не разбирают и не собирают, а передают как есть.

Курсор, а не `offset`, — потому что при добавлении операций смещение «съезжает» и записи на границе страниц дублируются или пропадают.

Короткие справочники (валюты) отдаются целиком, без пагинации, но в том же формате `{"items": [...]}`.

## Ошибки

Все ошибки под `/api` — в формате [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) (Problem Details), `Content-Type: application/problem+json`. Это касается и неизвестных адресов, и неподдерживаемых методов, и ошибок разбора и проверки запроса.

```json
{
  "type": "about:blank",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "Некорректные данные запроса.",
  "code": "validation_failed",
  "errors": [
    {"field": "amount", "code": "required", "message": "Обязательное поле."}
  ]
}
```

| Поле | Смысл |
|---|---|
| `type` | пока всегда `about:blank` |
| `title` | стандартная фраза HTTP-статуса |
| `status` | HTTP-статус |
| `detail` | пояснение для разработчика и запасной текст |
| `code` | **машиночитаемый код** — по нему клиент выбирает текст для пользователя |
| `errors` | только при `validation_failed`: ошибки по полям |

`errors[].field` — путь к полю в camelCase через точку (`amount`, `splits.0.amount`) или имя параметра запроса (`limit`). Формат совпадает с путями полей в `@mantine/form`, ошибку можно сразу показать у поля. `errors[].code` — вид нарушения: `required`, `invalid_type`, `invalid_value` (не из enum), `invalid_format`, `too_long`, `too_short`, `too_large`, `too_small`, `too_many_items`, `too_few_items`, `unknown_field`, `invalid` (прочее); сервисный слой добавляет свои.

Коды ошибок (список расширяется; неизвестный код клиент обрабатывает по HTTP-статусу):

| `code` | Статус | Когда |
|---|---|---|
| `bad_request` | 400 | запрос не удалось разобрать: невалидный JSON, тело там, где его быть не должно |
| `validation_failed` | 422 | запрос разобран, но данные не прошли проверку; подробности в `errors` |
| `unauthorized` | 401 | нет действующей сессии: cookie нет, сессия истекла, удалена или пользователь вышел |
| `invalid_credentials` | 401 | вход: неверный e-mail или пароль (один ответ на оба случая) |
| `forbidden_origin` | 403 | запрос, меняющий данные, пришёл со страницы другого сайта (защита от CSRF) |
| `not_found` | 404 | адрес или объект не найден (в т. ч. объект чужой семьи — не 403, чтобы не раскрывать факт существования) |
| `method_not_allowed` | 405 | метод не поддерживается для адреса; список допустимых — в заголовке `Allow` |
| `too_many_requests` | 429 | превышен лимит частоты; через сколько секунд повторить — в заголовке `Retry-After` |
| `account_has_transactions` | 409 | удаление счёта, на который ссылается хоть одна операция (в т. ч. удалённая или как получатель перевода); такой счёт можно только архивировать |
| `account_archived` | 409 | корректировка остатка архивного счёта; сначала его нужно вернуть из архива |
| `adjustment_readonly` | 409 | правка корректировки остатка: её можно только удалить (и вернуть) |
| `transaction_readonly` | 403 | правка, удаление или восстановление операции, у которой пользователь видит не все счета (перевод с чужого личного счёта на общий или обратно); может только владелец личного счёта |
| `internal` | 500 | непредвиденная ошибка |

**409 или 422.** 422 — исправь поля запроса (подсветка у полей). 409 `Conflict` — запрос корректен, но действие невозможно в текущем состоянии объекта; полей, которые можно исправить, нет. У каждого 409 свой `code`, по нему клиент показывает текст; в Go — `problem.Conflict(code, detail)`, коды — константы в `internal/problem`.

Коды бизнес-правил в `errors[].code` (ошибки полей при `validation_failed`):

| `errors[].code` | Поле | Когда |
|---|---|---|
| `email_taken` | `email` | регистрация на уже занятый e-mail |
| `invalid_token` | `token` | токен из письма неверный, просрочен, уже использован, выдан для другого назначения или для прежнего адреса пользователя (причина не уточняется) |
| `invalid_parent` | `parentId` | категории: родитель не подходит — его нет в семье (в т. ч. категория чужой семьи), он другого вида, сам подкатегория (глубина > 2), это сама категория; при создании или смене родителя — в архиве |
| `has_children` | `parentId` | категории: категорию с подкатегориями нельзя сделать подкатегорией |
| `name_taken` | `name` (создание, переименование) или `parentId` (перемещение) | категории: у соседей (тот же вид и родитель, включая архивные) уже есть такое имя; сравнение точное, с учётом регистра |
| `invalid_target` | `targetId` | слияние категорий: цели нет в семье (в т. ч. чужая), она другого вида, в архиве, это сама категория или её подкатегория |
| `invalid_account` | `accountId`, `toAccountId` | операции: счёта нет в семье (в т. ч. чужой семьи), он не виден пользователю (чужой личный) или в архиве. При правке счёт, который уже был у операции, может быть архивным |
| `same_account` | `toAccountId` | перевод: счета списания и зачисления совпадают |
| `invalid_category` | `categoryId` | операции: категории нет в семье, она другого вида, чем операция, или в архиве (при правке неизменённая категория может быть архивной) |
| `not_allowed` | `categoryId`, `toAccountId`, `toAmount` | операции: поле не бывает у этого вида (категория у перевода, счёт и сумма зачисления у расхода и дохода) |
| `to_amount_mismatch` | `toAmount` | перевод между счетами одной валюты: сумма зачисления не равна сумме списания |
| `invalid_range` | `to` | отчёты: конец периода раньше начала |
| `period_too_long` | `to` | отчёты: период 10 лет и длиннее (`to` не раньше `from` + 10 лет) |

Объект чужой семьи **в адресе** — 404, а **в теле** (`parentId`, `targetId`) — 422 с тем же кодом, что у несуществующего: 404 на `POST /categories/{id}/move` читался бы как «нет перемещаемой категории», а одинаковый ответ для чужого и несуществующего id не раскрывает факт существования.

**Почему 422, а не 400.** 400 — «запрос не понят»: это ошибка в клиентском коде, пользователю показать нечего. 422 — «понят, но данные не подходят»: клиент подсвечивает поля из `errors`. Разные статусы позволяют клиенту обрабатывать два случая по-разному, не разбирая тело. 422 возвращается для любых `validation_failed` — и от проверки по контракту, и от бизнес-правил.

При 500 клиент получает только общий текст. Подробности (текст ошибки, SQL, стек) пишутся в лог вместе с request id. Request id сервер возвращает в заголовке `X-Request-Id` — по нему ошибку пользователя находят в логах. Клиент может прислать свой `X-Request-Id` (до 64 символов `A-Za-z0-9._-`), иначе сервер сгенерирует его сам.

Если клиент сам отменил запрос (закрыл соединение), это не ошибка сервера: в лог пишется уровень info и статус 499.

В Go ошибка с известным кодом — это `*problem.Problem` из `internal/problem`: обработчик возвращает её как обычную ошибку (`return nil, problem.NotFound("Счёт не найден.")`). Любая другая ошибка превращается в 500. У `problem.TooManyRequests(d)` длительность уходит в заголовок `Retry-After` (секунды, с округлением вверх).

## Авторизация

Вход — по e-mail и паролю (`POST /auth/register`, `/auth/login`, `/auth/logout`, `GET /me`). Сессии хранятся в Postgres (таблица `sessions`), браузер держит только случайный токен в cookie. Подтверждение e-mail и сброс пароля — по ссылке из письма, см. «Подтверждение e-mail и сброс пароля».

### Cookie сессии

- Имя `pa_session`, значение — 32 случайных байта (`crypto/rand`) в base64url. В БД — только SHA-256 токена: утечка базы не даёт войти по чужой сессии.
- Флаги: `HttpOnly` (JavaScript её не видит), `SameSite=Lax`, `Path=/api` (не уходит с запросами за статикой), `Secure` — по настройке `COOKIE_SECURE` (по умолчанию включён в production и выключен в development, где API работает по http).
- Срок — 30 дней, **скользящий**: если с прошлого продления прошло больше часа, любой запрос с сессией продлевает `expires_at` и присылает обновлённый `Set-Cookie`. Просроченная сессия равна отсутствующей: при обращении она удаляется, ответ — 401.
- Регистрация и вход выдают новую сессию (вход при этом удаляет прежнюю сессию этого браузера), выход удаляет сессию из БД и стирает cookie (`Max-Age=0`). Выход идемпотентен: без сессии тоже 204.
- В сессии сохраняются `ip` (реальный, см. ниже) и `user_agent` (до 512 байт).

Пароли — argon2id (OWASP: m=19456 KiB, t=2, p=1, соль 16 байт, ключ 32 байта) в PHC-строке `$argon2id$v=19$m=…,t=…,p=…$соль$хеш`: параметры записаны в самом хеше, их можно поменять, не ломая старые. Длина пароля — 8–128 символов. При входе с несуществующим e-mail сервер всё равно проверяет пароль против фиктивного хеша, чтобы время ответа не выдавало, есть ли аккаунт.

### Какие операции требуют входа

Решает **контракт**, а не список путей в коде. В `openapi.yaml` глобально задано `security: [cookieAuth: []]` — по умолчанию каждая операция требует сессии. Публичная операция явно переопределяет это:

```yaml
  /currencies:
    get:
      operationId: listCurrencies
      security: []        # без входа
```

Сейчас публичные: `listCurrencies`, `register`, `login`, `logout`, `verifyEmail`, `requestPasswordReset`, `confirmPasswordReset`. Тест `TestContractSecurity` фиксирует этот список — новая публичная операция добавляется в него осознанно.

Middleware `authenticate` (`internal/httpapi/session.go`) находит операцию контракта для запроса и, если она не публичная, проверяет cookie. Нет действующей сессии — 401 `unauthorized` (и стирание мёртвой cookie) до валидатора и обработчика.

### Текущий пользователь в обработчике

```go
func (s *server) ListAccounts(ctx context.Context, req oapi.ListAccountsRequestObject) (oapi.ListAccountsResponseObject, error) {
	p := currentUser(ctx) // Principal{UserID, FamilyID, Role}
	rows, err := s.q.ListAccounts(ctx, dbgen.ListAccountsParams{FamilyID: p.FamilyID, UserID: p.UserID})
	...
}
```

`family_id` для запросов к доменным таблицам берётся **только** из `currentUser(ctx)`, никогда из тела или параметров запроса. `currentUser` паникует (→ 500), если вызвать его в публичной операции: это ошибка в коде, а не запрос клиента.

### Защита от CSRF

На всё под `/api` стоит `http.CrossOriginProtection` из стандартной библиотеки Go. Запросы, меняющие данные (POST, PUT, PATCH, DELETE), пропускаются, если:

- браузер прислал `Sec-Fetch-Site: same-origin` или `none`;
- или (браузеры без `Sec-Fetch-Site`, страница по http не на localhost) `Origin` совпадает с `Host`;
- или заголовков нет вовсе — запрос не из браузера (curl, серверный клиент); от CSRF защищать нечего.

Иначе — 403 `forbidden_origin`. `GET`/`HEAD` не проверяются: они не меняют данных. Вместе с `SameSite=Lax` это закрывает CSRF без токенов в формах.

Dev-сценарий проходит без настроек: страница на `localhost:5173`, Vite проксирует `/api` на `:8080`, браузер видит один origin и шлёт `same-origin`. С телефона (`http://192.168.x.x:5173`) `Sec-Fetch-Site` не приходит, но прокси Vite сохраняет `Host`, и он совпадает с `Origin`. Если фронт когда-нибудь окажется на другом origin, его можно разрешить переменной `CSRF_TRUSTED_ORIGINS` (через запятую, например `http://localhost:5173`).

### Ограничение частоты

| Что | Лимит | Ключ |
|---|---|---|
| `register` и `login` | 20 запросов в минуту | IP (для IPv6 — сеть /64) |
| `login` | 5 попыток за 15 минут; успешный вход сбрасывает счёт | e-mail + IP |
| `login` | 50 **неудачных** попыток в час; успешный вход счёт не сбрасывает | e-mail (со всех адресов) |
| `requestPasswordReset` | 20 запросов в час | IP |
| `requestPasswordReset` | 3 письма в час; превышение ответ **не** меняет (202), письмо просто не уходит | e-mail |
| `verifyEmail` и `confirmPasswordReset` | 20 запросов в минуту (общий) | IP |
| `resendVerificationEmail` | 1 в минуту и 5 в час | пользователь |
| `exportAll` | 10 в час | пользователь |

E-mail в ключах — в нижнем регистре. Окно скользящее. Превышение любого лимита (кроме лимита писем сброса на адрес) — 429 `too_many_requests` с `Retry-After`. Лимит сброса на адрес не даёт 429, иначе ответ выдавал бы, что адрес недавно запрашивали, — то есть что аккаунт, скорее всего, есть. Он учитывается для любых адресов, зарегистрированных и нет.

Лимиты задаются в `httpapi.Limits`, умолчания — `defaultLimits` в `internal/httpapi/router.go`.

- Лимит по IP стоит до проверки по контракту: невалидные запросы тоже его расходуют. Запрос входа с невалидным e-mail (в т. ч. с управляющими символами) отклоняется проверкой по контракту (422) и лимиты по e-mail не расходует.
- Лимит «e-mail + IP» учитывает попытку до проверки пароля, поэтому параллельные запросы не проскакивают его, пока считается хеш. IP в ключе нужен, чтобы посторонний не мог неверными паролями со своего адреса заблокировать владельцу вход с его адреса.
- Общий лимит на e-mail защищает от распределённого перебора с многих адресов.
- Несуществующий e-mail считается так же, как существующий.

**Остаточный риск:** распределённая атака (50 неудачных попыток в час с разных адресов) по-прежнему может заблокировать вход в чужой аккаунт — со всех адресов, включая адрес владельца, пока атака продолжается. Это цена защиты от распределённого перебора; смягчить можно позже (например, вход по ссылке из письма в обход лимита).

**Ограничение MVP:** счётчики живут в памяти процесса (`internal/ratelimit`). При нескольких экземплярах API у каждого свой счёт, после перезапуска счёт обнуляется. Для нескольких экземпляров понадобится общее хранилище (Postgres или Redis). Старые ключи удаляются раз в окно, память не растёт без предела. Лимиты и часы подменяются в тестах через `httpapi.Options`.

### Подтверждение e-mail и сброс пароля

| Операция | Вход | Ответ |
|---|---|---|
| `POST /auth/verify-email` `{token}` | не нужен (ссылку могут открыть в другом браузере) | 204 |
| `POST /auth/verify-email/resend` | нужен | 204; если e-mail уже подтверждён — тоже 204, письмо не отправляется |
| `POST /auth/password-reset` `{email}` | не нужен | **всегда** 202 без тела — есть такой аккаунт или нет |
| `POST /auth/password-reset/confirm` `{token, password}` | не нужен | 200 `Me` + новая cookie сессии |

Подтверждение **мягкое**: без него приложением можно пользоваться (`GET /me` отдаёт `emailVerified`). Письмо подтверждения отправляется при регистрации (после коммита транзакции) и по `resend`.

**Токены** (таблица `email_tokens`):
- 32 случайных байта в base64url (как у сессий), в БД — только SHA-256;
- сроки: подтверждение — 24 часа, сброс — 1 час (`verifyEmailTokenTTL`, `resetPasswordTokenTTL` в `internal/httpapi/email.go`; те же сроки — в текстах писем);
- одноразовые: погашение — один `UPDATE … WHERE used_at IS NULL AND expires_at > now RETURNING`, поэтому из двух одновременных запросов с одним токеном успешен только один;
- новый токен того же назначения удаляет прежние: действует только ссылка из последнего письма. Выдача токена блокирует строку пользователя (`SELECT … FOR UPDATE`), чтобы одновременные запросы не оставили два действующих токена;
- токен привязан к адресу, на который ушло письмо: если `users.email` сменился, токен недействителен;
- любой неподходящий токен — 422 `validation_failed` с ошибкой `invalid_token` у поля `token`.

**Сброс пароля** в одной транзакции гасит токен, меняет хеш пароля (правила — как при регистрации: 8–128 символов), подтверждает e-mail (владение адресом доказано), удаляет **все** сессии пользователя и создаёт новую. После коммита сбрасываются счётчики неудачных входов для этого e-mail и счётчик «e-mail + IP» для текущего IP (с других IP — нет: их ключи не перечислить, они истекут сами). Токен проверяется до расчёта хеша пароля: argon2id не считается для заведомо неверных токенов.

**Время ответа `password-reset`** не должно выдавать, есть ли аккаунт. В обработчике в обоих случаях — только поиск пользователя; токен создаётся и письмо отправляется в фоне.

**Ссылки в письмах:** `APP_BASE_URL` + `/verify-email?token=…` и `/reset-password?token=…` — это маршруты фронтенда; страница берёт `token` из адреса и отправляет его в API.

### Письма

Пакет `internal/mail`:
- `Mailer` — интерфейс отправки. Реализации: `SMTP` (стандартная `net/smtp`, учитывает таймаут контекста; STARTTLS, если сервер предлагает; вход PLAIN, если задан `SMTP_USERNAME`), `Memory` (запоминает письма, для тестов), `Discard`;
- письмо — `multipart/alternative`: `text/plain` и простой HTML (`html/template` экранирует подставленные значения), UTF-8, тело в quoted-printable, заголовки с кириллицей — encoded-word (`mime.QEncoding`);
- `Background` отправляет письма в фоне: каждое — в своей горутине с таймаутом 30 с (`mailSendTimeout` в `cmd/api`), ошибка — в лог (`mail: send failed` / `mail: prepare failed`) с `kind`, `user_id`, `request_id`; ни токен, ни ссылка, ни адрес в лог не попадают. При остановке сервер сначала дожидается текущих запросов, потом закрывает отправку (`Background.Close`: новые письма больше не запускаются, в лог — `mail: dropped, sender closed`) и ждёт писем, отправка которых уже началась (до 10 с). Тесты дожидаются писем через `Background.Wait`, без `time.Sleep`;
- адрес получателя разбирается `net/mail.ParseAddress`, в `RCPT TO` и `To` уходит только сам адрес. Валидатор контракта (`format: email`) принимает только адреса, которые `ParseAddress` разбирает в ту же строку, — иначе регистрация прошла бы, а письма молча не уходили бы.

В разработке письма принимает Mailpit (см. README). Production-провайдер выбирается на этапе 6.

**Ограничения MVP:** очереди писем (outbox) нет — письмо, отправка которого не закончилась до падения процесса, теряется; пользователь запросит его ещё раз. Ошибка SMTP клиенту не видна (ответ уже отправлен), только в логе.

### Реальный IP клиента

Middleware `withClientInfo` (первое в цепочке) определяет IP и кладёт его в контекст. IP используется в лимитах, в `sessions.ip` и в логе запросов (поле `ip`).

- Настройка `TRUSTED_PROXIES` — CIDR или отдельные IP через запятую (`10.0.0.0/8,172.16.0.1`), по умолчанию пусто.
- Если адрес соединения **не** из списка, клиент — сам адрес соединения, `X-Forwarded-For` игнорируется: его может прислать кто угодно.
- Если из списка — `X-Forwarded-For` читается справа налево (каждый прокси дописывает адрес в конец), доверенные адреса пропускаются, первый недоверенный — клиент. Значения левее него мог подделать сам клиент.

`middleware.RealIP` из chi не используется: он безусловно доверяет `X-Forwarded-For`.

### Курсы ЦБ РФ

Пакет `internal/rates` заполняет `exchange_rates` (смысл таблицы — в [data-model.md](data-model.md)). Эндпоинтов нет: таблицу читают запросы отчётов.

- **Источник** — только официальный XML-сервис ЦБ (`CBR_BASE_URL`, по умолчанию `https://www.cbr.ru/scripts`): `XML_daily.asp?date_req=ДД/ММ/ГГГГ` — список валют с внутренними кодами ЦБ (`R01235` — USD; коды берутся оттуда по `CharCode`, не хардкодятся) и `XML_dynamic.asp?date_req1=…&date_req2=…&VAL_NM_RQ=<код>` — история валюты за период одним запросом. Ответы в windows-1251: `encoding/xml` получает `CharsetReader` с таблицей windows-1251 (`charset.go`, без `golang.org/x/text`). Ошибку в параметрах ЦБ возвращает с HTTP 200 как `<ValCurs>Error in parameters</ValCurs>` — это ошибка, а не пустой ответ.
- **Без float.** Из `XML_daily` берутся только `ID` и `CharCode`: курсы в нём не проверяются и не используются, чтобы кривая запись чужой валюты не останавливала загрузку. В БД пишется только `XML_dynamic`: его `Value` («92,1234») проверяется как положительное десятичное число (не пустое, не ноль, без знака и экспоненты, до 12 знаков до и после запятой), `Nominal` — целое 1…1 000 000; дальше строка уходит в Postgres, и `round(value::numeric / nominal, 8)` считается там (`UpsertExchangeRates`).
- **Что загружается.** Все валюты из `currencies`, кроме RUB, включая неактивные. Нет курсов по валюте — вся история с 2000-01-01 (`rates.DefaultHistoryStart`); есть — с последней загруженной даты минус 7 дней (ЦБ изредка поправляет курс) по «завтра» по Москве включительно. Валюты нет в списке ЦБ — предупреждение в лог, не ошибка.
- **Запись** — одна пачка на валюту, `INSERT … ON CONFLICT (currency_code, rate_date) DO UPDATE … WHERE rate <> EXCLUDED.rate`: повторный запуск ничего не дублирует, поправка ЦБ обновляет строку, несколько экземпляров API друг другу не мешают (блокировка не нужна). Ошибка по одной валюте не мешает остальным и не трогает уже загруженное: разбор идёт до записи.
- **Фон в API** (`cmd/api`, выключается `RATES_SYNC=false`): синхронизация при старте и затем раз в 3 часа (`rates.DefaultInterval`); одна синхронизация ограничена 10 минутами, запрос к ЦБ — минутой. Ошибка — `rates: sync failed, retry on next tick` (warn), паника перехватывается (`rates: sync panicked`, error); API от курсов не зависит. При остановке контекст отменяется, запросы к ЦБ и БД прерываются (`rates: sync interrupted by shutdown`), сервер ждёт выхода цикла до закрытия пула БД.
- **Разовая загрузка** — `go run ./cmd/rates sync` (разработка, первый деплой): тот же код, ненулевой код выхода при любой ошибке. Первая загрузка USD и EUR с 2000 года (≈ 6 700 строк на валюту) занимает около секунды.
- **Тесты** — образцы настоящих ответов ЦБ в `internal/rates/testdata` (windows-1251, `.gitattributes`: `-text`) и синхронизация в реальный Postgres через `httptest`-заглушку ЦБ; сети в тестах нет.

## Проверка запросов

Запрос проверяется в два слоя.

**1. Контракт** — middleware `requestValidator` (kin-openapi) по спецификации, встроенной в бинарник (`oapi.GetSpec`). Срабатывает до обработчика, ответ — 422 `validation_failed` с `errors[]` по всем полям сразу (или 400, если тело не JSON). Проверяет всё, что выражается схемой:

- обязательные поля и параметры (`required`);
- типы, `enum`, `format` (`uuid`, `date`, `date-time`), `pattern`;
- `minLength`/`maxLength`, `minimum`/`maximum`, `minItems`/`maxItems`;
- лишние поля — **соглашение:** у каждого объекта в теле запроса `additionalProperties: false`, иначе опечатка в имени поля молча проигнорируется. Тест `TestContractRequestBodiesForbidAdditionalProperties` проверяет это для всего контракта;
- тело у операции без `requestBody` — 400.

Ответы по контракту не проверяются.

**2. Сервисный слой** — всё, что зависит от данных и пользователя:

- принадлежность семье: каждый запрос фильтрует по `family_id` из сессии; чужой объект — 404;
- видимость личных счетов;
- бизнес-правила: тип категории соответствует типу операции, глубина дерева категорий ≤ 2, у перевода разные счета, удаление счёта только без операций и т. п.

Ошибки сервисного слоя — тоже `problem.Validation(...)` с полями (или `problem.NotFound`, `problem.Conflict`), формат для клиента один.

`uniqueItems` (повторы в массиве) валидатор сообщает кодом `invalid` — отдельного кода для него нет.

`format: date` проверяется по-настоящему (`isValidDate` в `validator.go`): несуществующая дата вроде `2026-02-31` и год `0000` — `invalid_format` у поля или параметра, а не 400 от разбора тела. Ошибка элемента массива в параметре запроса — с индексом: `kind.0`.

## Счета

Операции — в контракте (тег `accounts`), код — `internal/httpapi/accounts.go`, SQL — `internal/db/queries/accounts.sql`.

- **Видимость.** Пользователь видит общие счета семьи и свои личные (`owner_user_id IS NULL OR owner_user_id = :user`). Чужой личный счёт и счёт чужой семьи — 404 на **любой** операции, включая `PUT /accounts/order` и `adjust-balance`. Общие счета меняет любой участник семьи. В ответе `visibility: private` значит «личный счёт текущего пользователя» — чужие личные в ответы не попадают.
- **Список** (`GET /accounts`) — все видимые счета, включая архивные; фильтрует клиент. Порядок: `sortOrder`, `created_at`, `id`. Остаток, `hasTransactions` и `baseBalance` считаются в том же запросе (без N+1).
- **`baseBalance`** — остаток в базовой валюте семьи по курсу на «сегодня» пользователя (см. «Пересчёт валют»); у счёта в базовой валюте равен `balance`, `null` — у валюты нет ни одного курса. Есть в каждом ответе со схемой `Account` (список, создание, правка, архив, корректировка).
- **Порядок.** Новый счёт получает `sortOrder` = максимум в его группе + 1 (общие и личные пользователя — разные группы). `PUT /accounts/order` ставит `sortOrder` = позиция в списке (с 0) в одной транзакции; хоть один невидимый или несуществующий id — 404, ничего не меняется. Номера в разных группах могут совпадать: группы показываются раздельно.
- **Корректировка** (`adjust-balance`): счёт блокируется (`SELECT … FOR UPDATE`), затем считается остаток, создаётся операция `adjustment` на разницу и запись в `audit_log` — в одной транзакции. Блокировка не даёт двум одновременным корректировкам посчитать разницу от одного остатка. С ней же конфликтуют все записи операций по счёту: создание (проверка внешнего ключа берёт `FOR KEY SHARE` на счёт), правка, удаление и восстановление (явный `FOR KEY SHARE` на счета операции, `LockTransactionAccounts`) — пока идёт корректировка, остаток счёта не меняется, и наоборот. Дата — «сегодня» в поясе пользователя (`users.timezone`). Разница 0 — операции нет, в ответе нет `transactionId`.
- **Удаление** — тоже под блокировкой счёта: проверка «нет операций» и `DELETE` в одной транзакции; нарушение внешнего ключа (операция появилась в обход блокировки) тоже даёт 409.
- **Имя** обрезается от пробелов; длину 1–100 проверяет контракт до обрезки, пустое после обрезки — `required`.
- **Суммы** в запросах (`initialBalance`, `balance`) — схема `MoneyAmount`: `int64` в пределах ±10^15, чтобы сумма остатков не переполнялась.

## Категории

`GET /categories` отдаёт все категории семьи обоих видов, включая архивные, плоским списком (порядок: `kind`, `sortOrder`, момент создания, `id`); дерево и фильтр архива — на клиенте. Отдельного `DELETE` нет: удаление — только слиянием (`POST /categories/{id}/merge`), потому что количество операций в категории наружу не отдаётся (операции на чужих личных счетах скрыты даже по факту существования, счётчик бы их раскрыл). Правила архива и слияния — в [data-model.md](data-model.md#категории).

- **Имя:** пробелы по краям обрезаются, после обрезки 1–60 символов. Коды ошибок у поля `name`: пустая строка — `too_short` (`minLength` контракта), только пробелы — `required`, длиннее 60 после обрезки — `too_long` (в контракте `maxLength: 100` — это длина до обрезки, сверх неё тоже `too_long`), управляющие символы — `invalid_format`.
- **Позиции.** Новая категория встаёт в конец соседей. `move {parentId, index}` — одна операция для перетаскивания: `index` — позиция среди новых соседей в порядке списка, **считая архивные** и не считая саму категорию; больше числа соседей — в конец. Старые и новые соседи перенумеровываются `1..n` в той же транзакции. `sortOrder` клиент только сравнивает.
- **Гонки.** Каждое изменение категорий, включая переименование, идёт в транзакции под `pg_advisory_xact_lock` по ключу семьи (`LockFamilyCategories`): изменения категорий одной семьи выполняются по очереди, две одновременные перенумерации не дают дублей позиций. Блокировка снимается в конце транзакции, чтение и другие семьи не ждут. Выбрана вместо `SELECT … FOR UPDATE` строк соседей: при перемещении соседей две группы (старые и новые), и порядок блокировки строк пришлось бы выдерживать вручную, чтобы не поймать взаимоблокировку. Гонку одинаковых имён в любом случае закрывает уникальный индекс → `name_taken`. Переименование тоже под блокировкой, хотя это один `UPDATE`: иначе оно и параллельный `move`/`merge` захватывают строку и кортеж индекса имени в разном порядке и ловят взаимоблокировку (`deadlock detected` → 500 вместо `name_taken`).

## Операции

Операции — в контракте (тег `transactions`), код — `internal/httpapi/transactions.go`, SQL — `internal/db/queries/transactions.sql`.

| Операция | Ответ |
|---|---|
| `GET /transactions` | лента: `items`, `nextCursor`, `days` |
| `GET /transactions/summary` | итоги по тем же фильтрам: `totals` |
| `GET /transactions/defaults` | умные значения быстрого ввода |
| `GET /transactions/{id}` | 200 `Transaction` |
| `POST /transactions` | 201 `Transaction` |
| `PUT /transactions/{id}` | 200 `Transaction`; тело как у создания, вид можно менять (расход ↔ доход ↔ перевод) |
| `DELETE /transactions/{id}` | 204, мягкое удаление — отмена создания в тосте |
| `POST /transactions/{id}/restore` | 200 `Transaction`, идемпотентно — отмена удаления |

Дублирования на сервере нет: клиент создаёт копию обычным `POST`.

- **Видимость.** Операция видна, если виден её счёт или счёт-получатель перевода (см. [data-model.md](data-model.md#видимость-счетов)). Невидимая, чужой семьи и несуществующая — 404 на любом эндпоинте; удалённая — 404 везде, кроме `restore`. Перевод «личный ↔ общий» другим участникам отдаётся со скрытой стороной: её `accountId`/`amount`/`currency` (или `toAccountId`/`toAmount`/`toCurrency`) — `null`, `counterparty` — владелец личного счёта `{id, name}`.
- **Права.** Править, удалять и восстанавливать можно, только если пользователь видит **все** счета операции, иначе 403 `transaction_readonly`. Корректировку (`kind: adjustment`) править нельзя — 409 `adjustment_readonly`, удалить и вернуть можно. Поле `editable` в ответе — «можно править и удалять»; у корректировки всегда `false` (клиент по `kind` понимает, что удалить её можно). Общие операции правит любой участник; автор операции (`author`) при правке не меняется.
- **Тело** (`TransactionRequest`). Расход и доход: `categoryId` обязательна (`required`), `toAccountId` и `toAmount` запрещены (`not_allowed`). Перевод: `toAccountId` обязателен, `categoryId` запрещена; между счетами одной валюты `toAmount` не передаётся или равен `amount` (иначе `to_amount_mismatch`), между разными — обязателен (обмен валют). Валюта операции — всегда валюта счёта. Счёт — своей семьи, видимый, неархивный (`invalid_account`; чужой и несуществующий неразличимы), `toAccountId ≠ accountId` (`same_account`). Категория — своей семьи, того же вида, активная (`invalid_category`). При правке счёт и категория, которые уже были у операции, могут быть архивными. Комментарий обрезается от пробелов, ≤ 500 символов, управляющие символы (кроме переносов строк и табуляции) — `invalid_format`. Правила, зависящие от вида, — в сервисном слое: в схеме они потребовали бы `oneOf` по виду, а с ним хуже и ошибки валидатора, и сгенерированные типы.
- **Суммы** — схема `TransactionAmount`: целое 1…10^13 минимальных единиц (до 100 млрд ₽ на операцию). Так `SUM(...)::bigint` в остатках переполнится только после ~900 тыс. предельных операций. В ответе суммы положительные; исключение — `amount` корректировки, он со знаком.
- **Лента.** Порядок: `date` ↓, затем `id` ↓ (uuidv7 ≈ момент создания) — по индексу `transactions_feed_idx`. `limit` 1–200, по умолчанию 50. Курсор — base64url от «дата|id» последней строки страницы, клиент его не разбирает; неразбираемый — 422 `invalid_format` у `cursor`. Сервер читает `limit + 1` строк: лишняя строка значит, что есть следующая страница. Лента и итоги дней читаются в одной транзакции `REPEATABLE READ`, поэтому `days` точно соответствуют `items`.
- **Фильтры** (лента и итоги): `from`, `to` (даты включительно), `kind`, `accountId`, `categoryId`, `authorId` (массивы — повторением параметра: `?kind=expense&kind=income`; значения одного параметра — «или», разные параметры — «и»), `q`. Перевод подходит под `accountId`, если подходит любая его **видимая** сторона. Категория верхнего уровня включает подкатегории. `q` — подстрока комментария без учёта регистра, «ё» = «е», `%`, `_` и `\` — обычные символы; пустая строка — без фильтра. Регистр приводит `lower(... COLLATE pg_c_utf8)`: он не зависит от локали сервера БД. Невидимый, чужой или несуществующий id в фильтре просто ничего не находит.
- **Итоги** — по валютам, только расходы и доходы, суммы положительные: `[{currency, expense, income}]`, порядок по коду валюты. Переводы и корректировки не входят, пересчёта в рубли нет (он — в отчётах, см. «Отчёты»). `days` в ленте — итоги каждой даты из `items` по **всем** операциям этой даты под теми же фильтрами, даже если день разрезан границей страницы; `summary` — по всем датам.
- **`defaults`** — по операциям текущего пользователя (`created_by`): `expenseAccountId`, `incomeAccountId` — счёт последнего расхода / дохода; `transfer` — пара счетов последнего перевода; `frequentCategories.expense` / `.income` — до 8 категорий по числу неудалённых операций за 90 дней по «сегодня» пользователя включительно (будущие даты не считаются), при равенстве — у кого последняя операция свежее (дата, затем момент создания). «Последний» — по моменту создания, не по дате операции. Только видимые неархивные счета и активные категории: если последний расход был на архивном счёте, берётся предыдущий подходящий. Нет данных — `null` / `[]`.
- **Журнал.** Создание, правка, удаление и восстановление пишут запись в `audit_log` в той же транзакции; формат снимков — в [data-model.md](data-model.md#журнал-изменений).
- **Гонки.** Создание, правка и восстановление берут **разделяемую** advisory-блокировку по ключу категорий семьи (`LockFamilyCategoriesShared`, ключ тот же, что у `LockFamilyCategories`): операции не ждут друг друга, но слияние, архив и другие изменения категорий (исключительная блокировка) ждут записи операций, и наоборот. Категория проверяется уже под блокировкой, поэтому слияние не может удалить её до коммита операции. Блокировка берётся **первой** — до блокировки строки операции (`LockTransaction`, `FOR UPDATE`): слияние тоже сначала берёт её, а потом меняет строки операций, так что порядок блокировок одинаковый и взаимоблокировки нет. Удаление операции категорию не проверяет и блокировку категорий не берёт. Правка, удаление и восстановление после блокировки строки операции берут `FOR KEY SHARE` на её счета (старые; новые при правке блокирует проверка внешнего ключа): иначе параллельная корректировка остатка (`FOR UPDATE` счёта) посчитала бы разницу от остатка, который тут же изменится. Порядок «advisory → строка операции → счета» не даёт цикла: корректировка держит только счёт и вставляет новую строку, ничего из этого списка не ждёт; удаление счёта до `DELETE` не доходит, если на счёт ссылается хоть одна операция (а заблокированная — ссылается); `FOR KEY SHARE` друг с другом не конфликтуют, а слияние категорий счета не блокирует. Если счёт удалили между проверкой и записью, нарушение внешнего ключа превращается в 422 `invalid_account` у соответствующего поля, а не в 500.
- **Производительность** (семья с 10 тыс. операций, в таблице 30 тыс., замер 2026-11-23): лента — первая и глубокая страница ~2–3 мс, с фильтрами до ~15 мс (поиск по комментарию — полный перебор операций семьи); итоги за всё время ~7–9 мс; запросы `defaults` по 1–3 мс. Отдельные индексы не понадобились.

## Пересчёт валют

Курсы — таблица `exchange_rates` (`currency_code`, `rate_date`, `rate numeric(20,8)` — рублей за **1** единицу валюты; номинал ЦБ вроде «за 100 иен» при загрузке уже поделён). Её наполняет загрузка курсов ЦБ; пропуски в выходные не заполняются. Наружу курсы не отдаются: API отдаёт только пересчитанные суммы.

- **Куда.** В базовую валюту семьи (`families.base_currency`). Курсы хранятся «рублей за единицу», поэтому пересчёт верен только для базы RUB — в MVP другой нет. Другая база потребует кросс-курса (`курс валюты / курс базы`); сейчас она **не поддерживается**.
- **Курс на дату D** — последний с `rate_date ≤ D`; если такого нет (дата раньше истории курсов), — первый с `rate_date > D`. Для базовой валюты курс = 1. Курс на «сегодня» (`baseBalance`) выбирается так же: будущие курсы не используются, пока есть хоть один не позже сегодняшнего.
- **Формула.** Минимальные единицы валюты → минимальные единицы базы: `amount × курс × 10^(minorUnits базы − minorUnits валюты)`.
- **Точность.** Без `float`: суммы складываются в `numeric` (`SUM(bigint)` в Postgres — `numeric`), умножение на курс точное, округление — **один раз** на каждое число ответа, `round(numeric)` («половина — от нуля»: 0,5 → 1, 2,5 → 3). Поэтому итог не обязан совпадать с суммой округлённых слагаемых: `total` отчёта по категориям может отличаться от суммы `items` на несколько копеек.
- **Нет ни одного курса валюты** — её суммы в отчёт не входят, код — в `missingRates` (пусто, если пересчитано всё); у счёта — `baseBalance: null`. Валюта попадает в `missingRates`, только если она что-то меняет в ответе: есть её операции под фильтрами (по категориям, по месяцам) или её счёт среди счетов баланса.
- **Где в коде.** Пересчёт — в SQL (`internal/db/queries/reports.sql`, CTE `fx`; то же выражение — в `ListAccounts` в `accounts.sql`). Сначала операции складываются в группы (валюта, дата и категория — или только валюта и дата), затем множитель считается в `fx AS MATERIALIZED` **один раз на уникальную пару (валюта, дата)** — поиском по первичному ключу `exchange_rates` — и присоединяется к группам. Без `MATERIALIZED` планировщик встраивал выражение в каждое место использования (`SUM`, оконная `SUM`, `FILTER` для `missing`) и искал курс 2–3 раза на группу.

## Отчёты

Операции — в контракте (тег `reports`), код — `internal/httpapi/reports.go`, SQL — `internal/db/queries/reports.sql`.

| Операция | Ответ |
|---|---|
| `GET /reports/categories?kind&from&to&accountId&authorId` | `{currency, total, items: [{categoryId, amount}], missingRates}` |
| `GET /reports/monthly?from&to&accountId&authorId` | `{currency, items: [{month, expense, income}], missingRates}` |
| `GET /reports/balance?from&to&accountId` | `{currency, step, items: [{date, balance}], missingRates}` |

- **Общее.** Суммы — целые минимальные единицы базовой валюты (`currency`), пересчитанные по курсу на дату операции или точки (см. «Пересчёт валют»). Только **видимые** счета, фильтр по `family_id`, без удалённых операций. Базовая валюта и сам отчёт читаются в одной транзакции `REPEATABLE READ`.
- **Период.** `from` и `to` (даты включительно) обязательны (`required` — от валидатора). `from > to` — 422 `invalid_range` у `to`. Период ограничен: `to` должен быть раньше, чем `from` + 10 лет (120 месяцев; 121 строка по месяцам, если концы — в середине месяца), иначе 422 `period_too_long` у `to`. Предел — с запасом для «за всё время» в MVP, а запросы остаются в бюджете времени (см. «Производительность»).
- **Фильтры** `accountId`, `authorId` — массивы, как в ленте (повторением параметра; значения одного — «или», разные — «и»), разбор общий с лентой (`newTxFilters`). Невидимый, чужой или несуществующий id просто ничего не находит (не 404 и не 422).
- **По категориям.** `kind` — `expense` или `income` (обязателен). `items` — плоско: сумма операций, записанных **прямо** в категорию (у родителя — только его собственные операции, подкатегории — отдельными строками); дерево, доли и «Прочее» собирает клиент. Архивные категории входят. Порядок — `amount` ↓, затем `categoryId`; строк с нулевой суммой нет (в т. ч. если пересчитанная сумма меньше половины копейки). `total` — точная сумма всех операций, округлённая один раз.
- **По месяцам.** Строка на каждый месяц, пересекающийся с периодом, по возрастанию; пустые — с нулями. `month` — первое число. Операции — только с датой внутри `[from, to]`, даже если концы — середина месяца. Курс — на дату каждой операции, не на конец месяца.
- **Переводы и корректировки** в отчёты по категориям и по месяцам не входят.
- **Баланс.** Шаг выбирает сервер по длине периода в днях (включительно): ≤ 31 — `day`, ≤ 184 — `week` (ISO, пн–вс), иначе `month`. Точки — последний день каждого шага, пересекающегося с периодом, обрезанный по `to`: первая — конец шага, в который попадает `from` (если `from` — воскресенье, первая неделя из одного дня), последняя — всегда `to`. Значение точки — Σ по счетам остатка на конец дня (`initial_balance` + все неудалённые операции с `op_date ≤ дата`: обе стороны переводов, корректировки) × курс на дату точки; **может быть отрицательным**. Начальный остаток действует «с начала времён» (у счёта нет даты открытия — упрощение). Счета: без `accountId` — видимые с `includeInTotal`, включая архивные (их остаток — часть истории); с `accountId` — ровно указанные видимые, независимо от `includeInTotal`. Каждая сторона перевода — изменение своего счёта, поэтому перевод «личный → общий» другой участник видит только общей стороной. Фильтра по автору нет: остаток — свойство счёта. Счетов не нашлось — все точки с нулями.
- **Без N+1.** Каждый отчёт — два запроса (базовая валюта и сам отчёт). Баланс: изменения остатков раскладываются по «корзинам» точек (`width_bucket(op_date − 1, points)` — число точек раньше даты), затем накопительная сумма по корзинам и пересчёт по курсу на дату точки.
- **Производительность** (замер 2026-11-24, `EXPLAIN ANALYZE`, по 4 прогона): 3 семьи по 10 тыс. операций за 3 года, счета семьи в RUB, USD и EUR, курсы USD и EUR по рабочим дням за 10 лет. По категориям за 3 года (и за 10 — данные те же) ~40–55 мс; по месяцам за 3 года ~32–39 мс, за 12 месяцев ~11–12 мс; баланс — 10 лет помесячно ~15–19 мс, 31 день по дням ~8–9 мс; `GET /accounts` ~4–6 мс. До вынесения курса в `fx` по категориям было ~145–160 мс, по месяцам ~67–91 мс (курс искался 3 раза на группу). Поиск курса — по разу на пару (валюта, дата): ~2200 обращений к `exchange_rates_pkey` за 3 года в двух валютах. Операции в отчётах по категориям и по месяцам за длинный период читаются по `transactions_account_idx` (по счетам семьи), за короткий (12 месяцев) — по `transactions_feed_idx`; баланс — полный просмотр `transactions` для стороны списания и `transactions_to_account_idx` для зачислений (таблица маленькая, планировщику так дешевле). Новые индексы не понадобились.

## Экспорт

Операции — в контракте (тег `export`), код — `internal/httpapi/export.go` (выгрузка) и `exportfmt.go` (формат ячеек, чистые функции).

| Операция | Ответ |
|---|---|
| `GET /export/transactions?from&to&kind&accountId&categoryId&authorId&q` | 200 `text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="operations-<дата>.csv"` |
| `GET /export/all` | 200 `application/zip`, `export-<дата>.zip`: `accounts.csv`, `categories.csv`, `transactions.csv` |

`<дата>` — «сегодня» в поясе пользователя (`YYYY-MM-DD`, имя латиницей — без `filename*`). Ответы с `Cache-Control: no-store`. Ошибки (401, 422 в параметрах, 429) — обычный Problem JSON. `GET` ничего не меняет, поэтому клиент качает файл ссылкой (`<a href download>`); адрес с фильтрами даёт сгенерированный `getExportTransactionsUrl(params)`. Хуки orval для этих операций не использовать: `apiFetch` ждёт JSON.

- **Формат для Excel по-русски.** UTF-8 с BOM (без него Excel читает файл в cp1251), разделитель `;` (запятая — десятичный знак), строки через CRLF, кавычки по RFC 4180 (`encoding/csv`: поле с `;`, кавычкой или переносом строки — в кавычках, кавычка удваивается; перенос строки внутри комментария сохраняется). Заголовки колонок — по-русски, первой строкой; пустая выгрузка — только заголовок.
- **Числа и даты.** Суммы — в основных единицах по `minor_units` валюты, с десятичной запятой, без разделителя разрядов и без знака валюты: `1234,50`, `-0,05`, у валюты без копеек — `7`. Перевод из минимальных единиц — целочисленно, над строкой цифр (`formatMinor`). Дата операции — `ДД.ММ.ГГГГ`, момент создания — `ДД.ММ.ГГГГ ЧЧ:ММ` в поясе пользователя: Excel сам распознаёт их как число и дату.
- **Защита от формул (CSV injection).** Текстовая ячейка пользователя (названия счетов и категорий, комментарий, имена), начинающаяся с `=`, `+`, `-`, `@`, табуляции или `\r`, получает в начале `'` — Excel покажет её как текст. Суммы и даты формирует сервер, они не экранируются (иначе `-100,00` перестал бы быть числом).
- **Колонки `transactions.csv`** (и `/export/transactions`): Дата; Вид; Счёт; Сумма; Валюта; Счёт зачисления; Сумма зачисления; Валюта зачисления; Личный счёт участника; Категория; Подкатегория; Комментарий; Автор; Создана.
  - Вид — «Расход», «Доход», «Перевод», «Корректировка». Валюта — код (`RUB`).
  - **Знаки.** Расход — с минусом, доход — без знака, корректировка — со своим знаком (изменение остатка, как в БД). У перевода обе суммы положительные: направление задают колонки «Счёт» → «Счёт зачисления», а знак у одной из сумм читался бы как «перевод в минус». Так сумма колонки «Сумма» по расходам и доходам одной валюты — чистый итог периода, а фильтр «Вид» в Excel отделяет переводы.
  - Категория и подкатегория — двумя колонками: у операции в подкатегории «Категория» — родитель (итоги по родителю — фильтром, без разбора строки). У перевода и корректировки пусто.
  - «Автор» — имя создателя операции, «Создана» — момент создания.
- **Видимость — как в ленте.** Те же правила и тот же запрос (`ListTransactions`), что у `GET /transactions`: чужие личные счета и операции только по ним не выгружаются, удалённые — тоже. У перевода «личный ↔ общий» другим участникам скрытая сторона пуста (счёт, сумма, валюта), а в колонке «Личный счёт участника» — имя владельца личного счёта (аналог `counterparty`): по ней видно, кто пополнил общий счёт или снял с него, а сам личный счёт не раскрывается. Отдельная колонка, а не имя в «Счёте»: колонка «Счёт» остаётся списком настоящих счетов для фильтра. У владельца обоих счетов колонка пустая.
- **Фильтры** `/export/transactions` — те же, что у ленты (разбор общий: `newTxFilters`), порядок тот же (дата ↓, момент создания ↓). Выгружаются все подходящие операции, без `limit` и курсора.
- **`accounts.csv`** — видимые пользователю счета, включая архивные, в порядке экрана «Счета»: Название; Тип; Валюта; Видимость («Общий» / «Личный»); Начальный остаток; Текущий остаток; В общем балансе; В архиве («Да» / «Нет»). Чужих личных счетов нет.
- **`categories.csv`** — оба дерева, включая архивные: Вид; Категория; Подкатегория; В архиве. Расходы, затем доходы; за категорией верхнего уровня — её подкатегории (в колонке «Категория» у них — родитель).
- **Согласованный срез.** Справочники и все операции читаются в одной транзакции `REPEATABLE READ` только для чтения: в полном экспорте текущие остатки счетов сходятся с операциями, а операция, добавленная во время выгрузки, в файл не попадает.
- **Потоком.** Файл не собирается в памяти: операции читаются пачками по 1000 (тот же `ListTransactions` с курсором) и сразу пишутся в ответ, zip — тоже потоком (`archive/zip` поверх соединения). До отправки заголовков читаются справочники и первая пачка — ошибка там становится обычным 500 Problem JSON. Ошибка посреди файла (заголовки и часть тела уже ушли) пишется в лог и **обрывает соединение** (`http.ErrAbortHandler`): клиент увидит сбой загрузки, а не обрезанный файл, похожий на целый. Поэтому ответ — свой тип `streamResponse` (реализует интерфейсы ответов strict-сервера), а не сгенерированный с `io.Reader`: с ним strict-сервер дописал бы Problem JSON в середину CSV.
- **Ограничение частоты.** Полный экспорт — 10 в час на пользователя (`Limits.ExportAllPerUser`, в памяти, см. «Ограничение частоты»): каждый читает все данные семьи, а нужен он редко (резервная копия, переезд); 10 оставляют запас на повторы после обрыва. `/export/transactions` не ограничен — это обычное действие из ленты, по цене как лента целиком.
- **Производительность** (замер 2026-11-25, Windows, Postgres 18 в Docker): 10 тыс. операций в семье — `/export/transactions` ~100–120 мс (1,3–1,8 МБ), `/export/all` ~100–150 мс (zip ~60–90 КБ); 60 тыс. — ~1 с. Пик кучи Go во время выгрузки — 3–6 МБ и от числа операций не зависит (одна пачка в памяти); всего выделяется ~2 КБ на операцию.

## Как добавить эндпоинт

Все команды — из каталога `api/`.

1. **Контракт.** Опиши операцию в `openapi.yaml`: `operationId` в camelCase (из него получится имя метода); операция по умолчанию требует входа, публичную помечай `security: []`; схемы запроса и ответа в `components/schemas`, ответ `default: $ref: "#/components/responses/Problem"`. Всё, что можно выразить схемой, выражай в ней (`required`, `enum`, `maxLength`, `minimum`, `format`), у объектов тела — `additionalProperties: false`: эти проверки выполнит валидатор, в обработчике их не повторяй.
2. **Генерация сервера.** `go generate ./...` — обновит `internal/oapi/oapi.gen.go` и встроенную спецификацию. Сборка упадёт на строке `var _ oapi.StrictServerInterface = (*server)(nil)` в `internal/httpapi/server.go`, пока метод не реализован, — так и задумано.
3. **SQL.** Добавь запрос в `internal/db/queries/<область>.sql` с аннотацией `-- name: GetAccount :one` (`:one`, `:many`, `:exec`). Каждый запрос к доменным таблицам фильтрует по `family_id`. Снова `go generate ./...` — sqlc обновит `internal/db/dbgen`. Если удалил `.sql`-файл, удали и его `.sql.go` в `dbgen`: sqlc старые файлы не стирает.
4. **Обработчик.** Реализуй метод `server` в `internal/httpapi/<область>.go`: возьми текущего пользователя (`currentUser(ctx)`, см. «Авторизация»), проверь бизнес-правила, вызови запрос из `s.q` (несколько изменений — в транзакции, см. ниже), преобразуй строки БД в типы `oapi`, верни типизированный ответ (`oapi.GetAccount200JSONResponse{...}`) или ошибку (`*problem.Problem` либо любую другую → 500). Для пустых списков создавай срез через `make`, чтобы в JSON был `[]`, а не `null`.
5. **Тест.** В `internal/httpapi/*_test.go`: роутер через `newRouter(t, logger, testdb.Pool(t))` (или `newAuthEnv(t, Options{...})` — с подменёнными часами и помощниками `register`/`send`, см. `auth_test.go`), запрос через `httptest`. Защищённой операции нужна cookie: `cookie, _ := e.register(t, uniqueEmail())`, затем `e.send(..., withCookie(cookie))`. Проверяй сырой JSON (имена полей), коды ошибок, бизнес-правила, изоляцию семей и видимость личных счетов. Правила схемы отдельно тестировать не нужно — их покрывают тесты валидатора.
6. **Проверка.** `gofmt -l .` (пусто), `go vet ./...`, `go test ./...`. Сгенерированный код коммитится вместе с изменением: CI проверяет, что `go generate ./...` не даёт diff.

### Транзакции

`server` хранит пул (`s.pool`) и запросы (`s.q`, `*dbgen.Queries`). Одиночный запрос — через `s.q`. Несколько изменений, которые должны примениться вместе (операция + запись в журнал изменений), — в транзакции:

```go
tx, err := s.pool.Begin(ctx)
if err != nil {
	return nil, err
}
// Rollback после Commit ничего не делает, поэтому defer безопасен:
// при любом раннем return транзакция откатится.
defer tx.Rollback(ctx)

q := s.q.WithTx(tx) // те же запросы, но внутри транзакции
if err := q.CreateTransaction(ctx, ...); err != nil {
	return nil, err
}
if err := q.InsertAuditLog(ctx, ...); err != nil {
	return nil, err
}
if err := tx.Commit(ctx); err != nil {
	return nil, err
}
```

## Соответствие типов

| PostgreSQL | Go (sqlc, `dbgen`) | OpenAPI | Go (oapi-codegen, `oapi`) |
|---|---|---|---|
| `uuid` | `uuid.UUID` | `string, format: uuid` | `openapi_types.UUID` (= `uuid.UUID`) |
| `bigint` (деньги) | `int64` | `integer, format: int64` | `int64` |
| `integer` / `smallint` | `int32` / `int16` | `integer` | `int` (с `format: int32` — `int32`) |
| `text`, `char(3)` | `string` | `string` | `string` |
| `boolean` | `bool` | `boolean` | `bool` |
| `date` | `time.Time` (полночь UTC) | `string, format: date` | `openapi_types.Date` — обёртка: `openapi_types.Date{Time: d}`, обратно `.Time` |
| `timestamptz` | `time.Time` | `string, format: date-time` | `time.Time` |
| `inet` | `netip.Addr` (NULL — `*netip.Addr`) | — | — |
| `numeric` (курсы) | `pgtype.Numeric` | — | — |
| enum (`account_type` и др.) | свой строковый тип (`dbgen.AccountType`) | `string, enum: [...]` | свой строковый тип в `oapi` — преобразование через `string(...)` |
| NULL-колонка | указатель (`*string`, `*time.Time`, `*uuid.UUID`) | необязательное поле или `nullable: true` | указатель |

`date` переопределён на `time.Time` (а не `pgtype.Date`), потому что `openapi_types.Date` — тоже обёртка над `time.Time`: преобразование — одна строка без проверки `Valid`. Переопределения — в `api/sqlc.yaml`.

`numeric` (курсы, точные промежуточные суммы) наружу не выходит и в Go не читается: пересчёт и округление — в SQL, запросы отдают уже `bigint` (см. «Пересчёт валют»). Если курс когда-нибудь понадобится отдать клиенту — строкой с десятичной записью, а не `number`, чтобы не терять точность.

## Инструменты генерации

`oapi-codegen` и `sqlc` закреплены в `api/go.mod` директивой `tool` и запускаются через `go tool <имя>` — отдельно ставить их не нужно, версия у всех одна.

| Инструмент | Конфиг | Результат |
|---|---|---|
| `oapi-codegen` (strict server для chi + встроенная спецификация) | `internal/oapi/oapi-codegen.yaml` | `internal/oapi/oapi.gen.go` |
| `sqlc` (pgx/v5) | `sqlc.yaml`; схема — прямо из `migrations/` | `internal/db/dbgen/` |

Клиент для фронтенда генерирует `orval` (devDependency в `web/package.json`): `pnpm generate:api` из `web/`.

| Инструмент | Конфиг | Результат |
|---|---|---|
| `orval` (хуки TanStack Query, `fetch`) | `web/orval.config.ts` | `web/src/shared/api/generated/` |

Базовый адрес `/api/v1` задан в конфиге orval (`baseUrl`), пути берутся из `paths`. Имя хука — из `operationId`: `listCurrencies` → `useListCurrencies()`. Запросы идут через свой мутатор `web/src/shared/api/http.ts`: он превращает Problem Details в `ApiError` с полями `status`, `code` (любая строка, не только перечисленные в контракте), `detail`, `fieldErrors` (`errors[]` → `{ поле: текст }`) и `requestId` (из `X-Request-Id`). Сгенерированный код коммитится, CI (`web.yml`) проверяет, что он совпадает с контрактом.

Сгенерированный код (Go и web) в `.gitattributes` помечен `eol=lf`: генераторы пишут LF, и с `core.autocrlf=true` на Windows иначе появлялся бы фиктивный дифф.

`sqlc` на Windows работает без gcc: при сборке без cgo он использует парсер Postgres, скомпилированный в WebAssembly (`wasilibs/go-pgquery`). CI запускает генерацию так же (`CGO_ENABLED=0`).

## Прочее

- `HEAD` на любой ресурс с `GET` работает (chi `middleware.GetHead`), ответ 405 содержит заголовок `Allow`.
- Реальный IP клиента — только от доверенных прокси (`TRUSTED_PROXIES`), см. «Авторизация → Реальный IP клиента».
- Поле `format: email` в контракте генерируется как `openapi_types.Email`, который проверяет формат сам и без обрезки пробелов. Поэтому у полей e-mail стоит `x-go-type: string`, а формат проверяет валидатор контракта (`validator.go`, пробелы по краям допускаются — сервер их обрезает).
- `oapi-codegen` во встроенной спецификации (`oapi.GetSpec`) пишет `operationId` с заглавной буквы (`Register`). Для сравнения с контрактом есть `operationID(route)`.
- Успешные `GET /healthz` не пишутся в лог запросов (их шлёт балансировщик каждые несколько секунд); неуспешные пишутся, причина отказа БД — отдельной строкой уровня warn.
