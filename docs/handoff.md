## 2. Принятые решения

Не пересматривать без явного запроса пользователя. Обоснования — в указанных документах.

**API** ([api.md](api.md)):
- Префикс `/api/v1`. JSON в camelCase. Деньги — целые минимальные единицы плюс код валюты, суммы в API положительные.
- Ошибки — `application/problem+json` с полем `code`:
  - ошибки данных → 422 `validation_failed` с `errors[]` по полям (путь через точку);
  - неразбираемый запрос → 400.
- Объект чужой семьи → **404**, а не 403: факт существования не раскрывается.
- Схемы тел запросов в контракте — с `additionalProperties: false` (проверяется тестом).
- Тип `date` в sqlc → `time.Time`. `numeric` (курсы) наружу не выходит: пересчёт делает сервер, клиент получает целые суммы в базовой валюте (этап 4, `feat/api-reports`).
- `middleware.RealIP` не используется. Реальный IP берётся из `X-Forwarded-For` только от прокси из `TRUSTED_PROXIES`.
- Публичность операции определяется контрактом (`security: []`), а не списком путей в коде. Без сессии → 401 `unauthorized`.
- Занятый e-mail при регистрации → 422 `email_taken`: раскрытие факта регистрации принято ради UX.
- `server` хранит `*pgxpool.Pool` и `*dbgen.Queries`. Транзакции: `Begin → q.WithTx(tx) → Commit`.

**Web** ([ux.md](ux.md), CLAUDE.md → «Фронтенд»):
- Основной цвет — indigo (выбран ради контраста; финальный цвет бренда пользователь может поменять).
- Копейки скрываются, если их нет. В ленте и списках суммы выравниваются по правому краю. В отчётах суммы округляются до рублей.
- Мобильная раскладка: ширина < `sm` **или** телефон в альбомной ориентации. Единый источник — `useMobileLayout()`. Пока окно открыто, его вид (sheet или модалка) не меняется.
- «Сегодня» считается по часовому поясу профиля (`todayIn(tz)`), `formatOpDate` требует `today` явно.
- Тема берётся из системы. Переключатель появится в настройках профиля на этапе 5.
- Эталоны скриншотов — только для win32. В CI идут только `@a11y`-тесты.
- Порог сравнения скриншотов — `threshold: 0.005` (2026-11-21): прежний 0.2 пропускал устаревшие эталоны. При ложных падениях — поднимать до 0.01–0.02, не возвращать 0.2.
- Плейсхолдеры в полях не используем — только подписи.
- Глобально (2026-11-21, `feat/web-auth`): поля `size="md"` высотой 44 px; hover у `variant="light"` светлее ради AA; у `Button component={Link}` подпись центрируется флексом.
- Выбранное состояние переключателей оформляется как активный пункт бокового меню (подложка primary-light, текст `--app-color-accent-text`) + рамка — ради контраста индикатора ≥ 3:1.

**Рамки MVP** ([requirements.md](requirements.md#8-вне-рамок-mvp)):
- Вход через Яндекс ID и Google исключён из MVP (2026-11-19). Вход в MVP — только по e-mail и паролю. Таблица `user_identities` остаётся в схеме пустой, удалять её не нужно.
- Онбординг «первый счёт → быстрый ввод» перенесён из этапа 1 в конец этапа 2 (2026-11-19), ветка `feat/web-onboarding`.

**Процесс:**
- Ветки: `<тип>/<область>-<суть>`. Слияние — `--no-ff` после «ок» пользователя (CLAUDE.md → «Git»).
- Worktree агента после завершения может остаться заблокированным (`locked`, процесс Claude): если он чистый и ветка влита — `git worktree unlock`, затем `remove`.
- Исполнители — по умолчанию на **Opus** с effort **medium** (решение пользователя от 2026-11-19). Ревьюер на **Opus** — для новой функциональности. Правки после ревью проверяет сам PM, повторное ревью не заказывается.

## 4. Как PM ведёт задачу

1. **Постановка.** Цель, рамки («что НЕ делать»), заранее принятые решения, критерии приёмки со ссылками на документы, имя ветки, проверки перед отчётом, формат отчёта. Шаблон — в разделе 6.
2. **Исполнитель:** `Agent`, `isolation: "worktree"`, `run_in_background: true`, по умолчанию `model: "opus"`, `effort: "medium"`. Независимые задачи (например, `api/` и `web/`) можно запускать параллельно.
3. **Приёмка PM по отчёту исполнителя.** Не верить отчёту на слово:
   - в worktree прогнать сборку, линтер, тесты, генерацию без diff;
   - для UI — самому посмотреть скриншоты (инструмент `Read` открывает PNG).
4. **Ревью** — отдельный агент (шаблон в разделе 6), для новой функциональности. Ревьюер не правит код.
5. **Правки по ревью.** PM решает, что исправлять, и выбирает из предложенных вариантов. Список правок отправляется **тому же исполнителю** через `SendMessage`: у него сохранился контекст. Потом PM снова проверяет сам.
6. **Документация.** Правки в `docs/` и `CLAUDE.md`, которых не касаются ветки, PM делает в основной копии. Пробное слияние без изменений в репозитории: `git merge-tree --write-tree main <ветка>`.
7. **Отчёт пользователю.** Что сделано; что проверено и чем; что **не** проверено; решения PM, которые пользователь может оспорить. Затем запросить «ок» на слияние.
8. **Слияние.**
   - `git merge --no-ff -F <файл>` (`-F -` в этом окружении не работает, сообщение — через файл в scratchpad).
   - Проверки на `main`; убедиться, что `git diff <ветка> main -- api` (или `-- web`) пуст.
   - `git worktree remove`, `git branch -d`.
   - Обновить этот документ.

**Окружение (Windows):**
- Docker Desktop должен быть запущен.
- Postgres из `docker-compose.yml` общий для всех worktree: имя проекта зафиксировано (`name: personal_accounting`), поэтому `docker compose up -d` из worktree не поднимает второй контейнер. Тестовые БД изолированы, а dev-БД `pa` — общая.
- Playwright в разных worktree запускать на разных портах: `E2E_PORT=4181`.
- Ручная проверка web против настоящего API из worktree: API на свободном порту, `APP_BASE_URL` → адрес dev-сервера фронта, `pnpm dev` с `API_PROXY_TARGET`. Письма — в Mailpit (`http://localhost:8025`, API `/api/v1/messages`).
- Go 1.25 в системе сам подтягивает toolchain 1.26 (`GOTOOLCHAIN=auto`). sqlc работает с `CGO_ENABLED=0`, используется WASM-парсер.

### 5.3 `feat/api-auth-email` — ✅ влита (`27c05d2`)

Постановка ниже сохранена для истории; итог — в docs/api.md («Письма», «Ограничение частоты»). Отличия от постановки:
- токен сброса создаётся в фоне вместе с письмом (ради одинакового времени ответа);
- формат `email` дополнительно проверяется через `net/mail.ParseAddress` — на всех операциях, а не только при регистрации;
- после сброса очищаются счётчики неудачных входов по e-mail и «e-mail + IP» для текущего IP.

Ревью (Opus, безопасность): блокеров нет; 4 мелочи исправлены, TLS-режим SMTP отложен (техдолг №21).

**Цель.** Пользователь подтверждает e-mail по ссылке из письма и может восстановить доступ, если забыл пароль. Письма в dev видны в Mailpit.

**Решения:**
- **Подтверждение «мягкое».** Сразу после регистрации приложением можно пользоваться: цель «первая операция за ≤ 2 мин» важнее. Неподтверждённый e-mail в будущем ограничит только приглашения в семью (этап 5). `GET /me` уже отдаёт `emailVerified`.
- **Эндпоинты:**
  - `POST /auth/verify-email` `{token}` → 204; публичный, ссылку могут открыть в другом браузере;
  - `POST /auth/verify-email/resend` → 204; требует входа; если e-mail уже подтверждён — тоже 204;
  - `POST /auth/password-reset` `{email}` → 202 **всегда**, есть такой аккаунт или нет;
  - `POST /auth/password-reset/confirm` `{token, password}` → 200 `Me` + новая cookie.
- **Токены** (`email_tokens`, таблица уже есть):
  - 32 байта, в БД только SHA-256;
  - одноразовые (`used_at`), сроки: подтверждение — 24 ч, сброс — 1 ч;
  - новый токен того же назначения гасит прежние неиспользованные;
  - токен привязан к `email`: если адрес сменился, токен недействителен;
  - неверный, просроченный или использованный токен → 422 по полю `token`, код `invalid_token`.
- **Сброс пароля:**
  - удаляет **все** сессии пользователя и создаёт новую: пользователь сразу внутри;
  - подтверждает e-mail, если он ещё не подтверждён: владение адресом доказано.
- **Ссылки в письмах:** `APP_BASE_URL` + `/verify-email?token=…` и `/reset-password?token=…`. Это маршруты фронта, их делает `feat/web-auth`. В dev `APP_BASE_URL` = `http://localhost:5173`.
- **Отправка писем:**
  - интерфейс `Mailer` с реализациями SMTP на `net/smtp` (без зависимостей) и in-memory для тестов;
  - письма отправляются фоном (горутина с таймаутом, ошибки — в лог), чтобы время ответа `password-reset` не выдавало, есть ли аккаунт. Очередь (outbox) — не в MVP, записать в техдолг;
  - тексты на русском, `text/plain` + простой HTML через `html/template`;
  - регистрация отправляет письмо подтверждения.
- **Mailpit** в `docker-compose.yml`: SMTP `1025`, веб-интерфейс `8025`. Переменные `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `MAIL_FROM`; умолчания — под Mailpit.
- **Rate limit:**
  - `password-reset` по IP и по e-mail (не чаще 3 писем в час на адрес);
  - `resend` — не чаще раза в минуту и 5 раз в час на пользователя;
  - `confirm` и `verify-email` — по IP.

**Рамки:** смена e-mail, смена пароля из профиля и экраны — не здесь.

**Критерии приёмки:**
- тесты на реальном Postgres:
  - полный цикл подтверждения и сброса;
  - повторное использование токена, просроченный токен, токен после смены адреса;
  - одинаковый ответ `password-reset` для существующего и несуществующего e-mail;
  - сброс завершает старые сессии;
  - лимиты;
  - письмо уходит при регистрации (in-memory mailer);
- ручная проверка: письма видны в Mailpit, ссылки ведут на `APP_BASE_URL`;
- документация: README (Mailpit, переменные), docs/api.md (эндпоинты, коды ошибок).

**Модель:** Opus, effort medium. Ревью: Opus — безопасность.

### 5.4 `feat/web-auth` — ✅ влита (`258ebd9`)

Постановка ниже сохранена для истории; итог — в разделе 1 и CLAUDE.md. Отличия и уточнения PM к постановке:
- `/verify-email` подтверждает автоматически при открытии (один запрос и в StrictMode), без входа; если ссылка недействительна, а адрес уже подтверждён — «Адрес уже подтверждён»;
- после сброса пароля — сразу на главную с тостом;
- плашку можно скрыть до следующего входа (`sessionStorage`);
- ошибка сети при выходе — тост, пользователь остаётся;
- глобальные правки темы и стилей — см. раздел 2 «Web».

Ревью (Opus, UX + редиректы): блокеров нет, open redirect не найден. Исправлено 6 находок: контраст выбранного сегмента, окно быстрого ввода поверх `/login` после 401, горизонтальный скролл при 200 %, устаревшие эталоны (порог скриншотов ужесточён до 0.005), публичность путей со `/` на конце и в другом регистре, текст «Адрес уже подтверждён».

Исходная постановка: Хуки orval: `useRegister`, `useLogin`, `useLogout`, `useGetMe`, `useVerifyEmail`, `useResendVerificationEmail`, `useRequestPasswordReset`, `useConfirmPasswordReset`. Коды ошибок: `invalid_credentials`, `email_taken`, `invalid_token` (поле `token`), `too_many_requests` (секунды — в `Retry-After`), `validation_failed` — см. docs/api.md. `password-reset` всегда отвечает 202: экран показывает «если аккаунт есть, письмо отправлено». `confirm` возвращает `Me` и cookie — после него пользователь сразу внутри.

**Цель.** Человек регистрируется, входит, восстанавливает пароль и подтверждает e-mail. Неавторизованного пользователя приложение не пускает дальше экрана входа.

**Решения:**
- **Маршруты** — вне оболочки (`AppShell`), по центру экрана; на mobile — во всю ширину:
  - `/login` и `/register` — одна форма с переключателем «Вход / Регистрация» (roadmap, этап 1); два адреса, чтобы на каждый можно было дать ссылку;
  - `/forgot-password`, `/reset-password?token=`, `/verify-email?token=`;
  - `/legal/privacy`, `/legal/terms` — страницы-заглушки.
- **Регистрация:**
  - поля: имя, e-mail, пароль (кнопка «показать пароль», без поля повтора) и чекбокс согласия со ссылками на документы;
  - часовой пояс не спрашиваем: берём `Intl.DateTimeFormat().resolvedOptions().timeZone`;
  - `autocomplete`: `name`, `email`, `new-password` / `current-password` — чтобы работали менеджеры паролей.
- **Ошибки:**
  - `fieldErrors` из `ApiError` → ошибки у полей формы;
  - `invalid_credentials` → сообщение над формой;
  - `too_many_requests` → «попробуйте через N мин»;
  - сетевая ошибка → введённое не теряется (ux.md §4).
- **Плейсхолдеры:** не используем, только подписи у полей. Иначе понадобится цвет `placeholder` с контрастом AA (техдолг №6).
- **Защита маршрутов:**
  - источник правды — `GET /me` в кэше TanStack Query;
  - 401 на любом запросе → сброс кэша и переход на `/login?next=<путь>`;
  - `next` принимаем только как относительный путь внутри приложения (защита от open redirect);
  - вошедший пользователь на `/login` перенаправляется на главную.
- **Выход:** пункт в «Ещё» на mobile и в боковом меню на desktop. Выход сбрасывает весь кэш запросов.
- **Неподтверждённый e-mail:** спокойная плашка в оболочке «Подтвердите e-mail — письмо отправлено на …» с кнопкой «Отправить ещё раз». Её можно скрыть до следующего входа.
- **Часовой пояс:** хук, отдающий `timezone` из `/me`. Через него вызывать `todayIn` вместо текущего источника.
- **e2e:**
  - скриншоты и axe для экранов входа, регистрации, восстановления пароля и состояния ошибки;
  - API подменяется через `page.route`, потому что под `vite preview` бэкенда нет.

**Онбординг** — не в этой ветке: перенесён в конец этапа 2 (`feat/web-onboarding`, решение пользователя от 2026-11-19). После регистрации пока показывается главная с пустым состоянием.

**Модель:** Opus, effort medium. Ревью: Opus — UX-чек-лист и безопасность редиректов.

**Решения PM (2026-11-23), пользователь может оспорить:**
- **Итоги — по валютам и только расходы/доходы.** Пересчёта в рубли до этапа 4 нет, поэтому итоги дня и выборки — списком `{currency, expense, income}`. Переводы и корректировки в итоги не входят (как в отчётах, requirements 5.10).
- **Итог дня считает сервер** — по всем операциям дня под теми же фильтрами, даже если день разрезан границей страницы.
- **Дублирование — на клиенте:** форма, заполненная копией, с датой «сегодня». Отдельного эндпоинта нет: копия — это обычное создание.
- **Отмена создания** — `DELETE`, **отмена удаления** — `POST /transactions/{id}/restore`. Корректировку можно удалить (и вернуть), но не править: это закрывает «Отменить» в тосте корректировки (№32).
- **Перевод «личный ↔ общий» для остальных участников:** скрытая сторона приходит как `null` (счёт, сумма, валюта), вместо неё — владелец личного счёта (`counterparty`). Такой перевод правит и удаляет только владелец личного счёта, остальным — 403 `transaction_readonly`. Поле `editable` в ответе.
- **Фильтр «автор»** есть в API, на web его нет до этапа 5: сейчас в семье всегда один человек. `MeFamily.memberCount` — чтобы web показывал автора только при > 1 участника.
- **Сумма операции** — 1…10^13 минимальных единиц (100 млрд ₽). Так переполнение `SUM(...)::bigint` (№29) потребует ~900 тыс. операций на предельную сумму — далеко за расчётными 10 тыс.
- **Журнал операций — снимок в формате API** (camelCase, положительные суммы, как в ответе). Корректировка переходит на тот же формат. Старые снимки корректировок (snake_case) есть только в dev-базах — миграции данных нет (production ещё не было).

#### Постановка `feat/api-transactions`

**Цель.** API, на котором web построит быстрый ввод, ленту и главную: операции всех видов с правкой, удалением, отменой, журналом и правилами видимости.

**Рамки:** просмотр истории операции (P1), список участников семьи и смена видимости счёта (этап 5), курсы и пересчёт в рубли (этап 4), экспорт — не здесь. Web не трогать, кроме `pnpm generate:api` (контракт меняется).

**Контракт** (тег `transactions`; имена — ориентир, отклонения обосновать в отчёте):
- Схема `Transaction`: `id`, `kind` (`expense|income|transfer|adjustment`), `date`, `accountId`, `amount` (положительная), `currency`, `toAccountId`, `toAmount`, `toCurrency`, `categoryId`, `comment`, `author` (`{id, name}` или `null`, если пользователь удалён), `counterparty` (`{id, name}` — владелец скрытого личного счёта, иначе `null`), `editable`, `createdAt`, `updatedAt`. Поля стороны, скрытой от пользователя, — `null`.
- `GET /transactions` — лента. Порядок: `date` ↓, затем `id` ↓ (uuidv7 ≈ момент создания; индекс `transactions_feed_idx`). Параметры: `from`, `to` (даты включительно), `kind` (несколько), `accountId` (несколько; перевод подходит, если подходит любая сторона), `categoryId` (несколько; категория верхнего уровня включает подкатегории), `authorId` (несколько), `q` (поиск в комментарии без учёта регистра и ё/е; `%` и `_` экранируются), `limit` (по умолчанию 50, максимум 200), `cursor`. Ответ: `items`, `nextCursor`, `days` — итоги каждой даты, попавшей в `items`, по всем операциям этой даты под теми же фильтрами: `[{date, totals: [{currency, expense, income}]}]`. Невидимый или чужой id в фильтре — просто ничего не находит (не 404 и не 422). Неразбираемый курсор — 422 по полю `cursor`.
- `GET /transactions/summary` — те же фильтры без курсора: `{totals: [{currency, expense, income}]}`.
- `GET /transactions/{id}`; `POST /transactions` (201); `PUT /transactions/{id}` (тело как у создания, вид менять можно: расход ↔ доход ↔ перевод); `DELETE /transactions/{id}` (204, мягко); `POST /transactions/{id}/restore` (200 `Transaction`, идемпотентно).
- Тело создания и правки: `kind` (`expense|income|transfer`), `date`, `accountId`, `amount`, `categoryId` (расход/доход), `toAccountId`, `toAmount` (перевод), `comment` (обрезка пробелов, ≤ 500). У перевода в одной валюте `toAmount` не передаётся или равен `amount`; в разных — обязателен.
- `GET /transactions/defaults` — умные значения для быстрого ввода текущего пользователя: последний счёт расхода/дохода, последняя пара счетов перевода, частые категории по видам (до 8, по числу операций пользователя за 90 дней, при равенстве — по свежести). Только видимые, неархивные счета и активные категории; нет данных — `null` / пустой список.
- `MeFamily.memberCount`.

**Правила:**
- Видимость: операция видна, если виден `account_id` или `to_account_id` (data-model.md → «Видимость счетов»); невидимая — 404 на любой операции; удалённая — 404 везде, кроме `restore` (он тоже проверяет видимость).
- Правка и удаление: можно, только если видны все счета операции, иначе 403 `transaction_readonly`. `PUT` корректировки — 409 `adjustment_readonly`; `DELETE` и `restore` корректировки разрешены (техдолг №32).
- Счёт в теле: видимый, неархивный, своей семьи, иначе 422 `invalid_account` у поля. Исключение — при правке счёт не менялся (старую операцию на архивном счёте можно поправить). `toAccountId = accountId` — 422 `same_account`. Категория: своей семьи, того же вида, активная (исключение — не менялась), иначе 422 `invalid_category`. Валюта — всегда валюта счёта. Несуществующие даты вроде `2026-02-31` — 422, не 500 (техдолг №9).
- Гонки: запись операции с категорией берёт **разделяемую** advisory-блокировку по тому же ключу, что `LockFamilyCategories` (`pg_advisory_xact_lock_shared`): операции не ждут друг друга, но не пересекаются со слиянием категорий (№30). Нарушение внешнего ключа (счёт удалили параллельно) — 422 `invalid_account`, не 500.
- Журнал (`audit_log`, в той же транзакции): `create` / `update` / `delete` / `restore`, `before` и `after` — снимок в формате `Transaction` без вычисляемых полей (`editable`, `author.name`, `counterparty`). `adjust-balance` переходит на тот же формат (№31). Обновить data-model.md → «Журнал изменений».
- Суммы: `amount`, `toAmount` — 1…10^13 (новая схема, `MoneyAmount` не трогать).
- Производительность: лента и итоги на 10 тыс. операций в семье — проверить `EXPLAIN ANALYZE`, p95 < 300 мс (requirements §7); результат — в отчёт.

**Критерии приёмки:**
- тесты на реальном Postgres: все виды операций, правка со сменой вида и счёта (в т. ч. в другой валюте), удаление и восстановление, журнал по каждому действию; фильтры по одному и в сочетании, курсор без пропусков и дублей при одинаковых датах, итоги дня через границу страницы; `defaults`;
- изоляция семей на каждом эндпоинте; видимость: второй участник (`addMember`) не видит операций по чужому личному счёту, видит перевод «личный → общий» со скрытой стороной и `counterparty`, получает 403 на правку и удаление; фильтр по чужому личному счёту ничего не находит; итоги не включают невидимое;
- гонка «операция ↔ слияние категории» — тест или обоснование в отчёте;
- docs/api.md (раздел «Операции», новые коды ошибок), data-model.md (журнал, видимость переводов), handoff не трогать;
- `pnpm generate:api` в `web/`, сгенерированный клиент закоммичен, `pnpm typecheck` проходит.

**Модель:** Opus, effort medium. Ревью: Opus — видимость, изоляция, гонки.

**Решения PM по курсам (`feat/api-rates`), пользователь может оспорить:**
- Источник — официальный XML ЦБ: `XML_daily.asp` (курсы на дату, из него же — внутренние id валют ЦБ) и `XML_dynamic.asp` (история по валюте одним запросом). Неофициальные зеркала (cbr-xml-daily.ru) не берём.
- Загружаются все валюты справочника, кроме базовой (RUB): USD и, с запасом, неактивный EUR. Курс = `Value / Nominal`, в `exchange_rates.rate` — «рублей за 1 единицу». Разбор без `float`: десятичная запись передаётся в Postgres строкой.
- Дата курса — дата, с которой ЦБ его устанавливает (атрибут `Date` у `ValCurs`/`Record`). Пропуски (выходные) не заполняются: правило «ближайший предыдущий» — при чтении.
- История — с 2000-01-01 (≈ 6,5 тыс. строк на валюту, один запрос). Операции раньше — по ближайшему следующему курсу (правило чтения, `feat/api-reports`).
- Обновление — фоновая горутина в процессе API: при старте догружает недостающее, затем раз в 3 часа. Запись идемпотентна (`ON CONFLICT DO UPDATE` — ЦБ может поправить курс), поэтому несколько экземпляров API друг другу не мешают. Ошибка ЦБ — предупреждение в лог и повтор на следующем такте. Выключается переменной (тесты, работа без сети). Отдельный планировщик (cron) не нужен до масштабирования.
- `go run ./cmd/rates sync` — разовая догрузка (dev, первый деплой).

**Решения PM по отчётам и пересчёту (`feat/api-reports`), пользователь может оспорить:**
- **Пересчёт** — в базовую валюту семьи (`families.base_currency`, в MVP всегда RUB). Курс на дату операции: ближайший предыдущий, если его нет — ближайший следующий. Суммируется точно (`numeric`), округление — один раз на каждое отдаваемое число, «половина от нуля». Валюта без единого курса → её операции не входят в отчёт, код валюты — в `missingRates` ответа; web предупреждает.
- **Отчёты считает сервер**, суммы — в минимальных единицах базовой валюты, только по видимым счетам. Переводы и корректировки в отчёты по категориям и по месяцам не входят (requirements 5.10). Невидимый или чужой id в фильтре ничего не находит (как в ленте).
- **По категориям** отдаётся плоским списком `{categoryId, amount}` — сумма операций, записанных прямо в эту категорию; дерево, доли, «Прочее» (> 8 сегментов) собирает web из списка категорий, который у него уже есть.
- **По месяцам** — все месяцы диапазона, пустые с нулями (для графика).
- **Баланс** — шаг выбирает сервер: ≤ 31 дня — день, ≤ 184 дней — неделя (ISO, пн–вс), дальше — месяц; точка — конец шага (последний — `to`). Значение — остаток на конец дня по курсу этого дня. Счета — видимые с `includeInTotal` (архивные тоже: в прошлом на них были деньги), с фильтром `accountId` — ровно указанные. Начальный остаток считается действующим «с начала времён» (упрощение, как у корректировки остатка). Фильтра «участник» у баланса нет — у остатка нет автора.
- **`Account.baseBalance`** — остаток по последнему курсу с датой ≤ «сегодня» пользователя; у рублёвых счетов равен `balance`; `null`, если курсов валюты нет. Общий баланс на главной web считает суммой `baseBalance`.
- Итоги ленты остаются по валютам, без пересчёта (они точные; пересчёт там не просили).

Итоги `feat/api-rates` (ревью Opus): из `XML_daily` берутся только `ID`/`CharCode` — строгая проверка курсов всех ~55 валют ЦБ останавливала бы загрузку USD/EUR из-за одной кривой записи чужой валюты (у IRR номинал уже 10^6); строго проверяется только `XML_dynamic`; окно догрузки — 7 дней назад … «завтра» по Москве (поправки ЦБ старше недели не подхватываются); без новых зависимостей (свой декодер windows-1251). Техдолг №48, №49.

Итоги `feat/api-reports` (ревью Opus):
- коды `invalid_range` (`from > to`) и `period_too_long` (`to ≥ from + 10 лет`), оба — по полю `to`; длина периода для шага — в днях включительно;

- курс ищется один раз на пару (валюта, дата) — CTE `fx AS MATERIALIZED`; на 10 тыс. операций в 3 валютах: категории ~50 мс, месяцы ~35 мс, баланс ≤ 20 мс, `GET /accounts` ≤ 7 мс. Техдолг №50.

Итоги `feat/web-currency` (ревью Opus): итог — Σ `baseBalance` в BigInt, округление один раз; `Money` принимает `bigint`; эквивалент под счётом всегда до рублей (и на «Счетах»: копейки изображали бы точность, которой у курса нет), итог «Счетов» — с копейками; валюта с нулевым итогом не упоминается; «≈» скрыт от скринридера (читается «примерно»), скрытый текст не копируется; по ревью — суммы в пояснениях переносятся целиком (`inline-block`), валюты без курса — строкой, а не второй крупной суммой. Техдолг №51–52.

**Решения PM по web (черновик, уточнится в постановках №3–5):**

- вкладки и фильтры отчётов — в адресе (`/reports/categories?from=…`), как фильтры ленты; пресеты периода: текущий месяц (по умолчанию), прошлый месяц, год, свой; фильтр «участник» — только при `memberCount > 1`;
- сначала вывод текстом (ux.md §3 «Отчёты»): сравнение с предыдущим месяцем — для пресетов «месяц», с прошлым годом — для «год», для своего периода сравнения нет;
